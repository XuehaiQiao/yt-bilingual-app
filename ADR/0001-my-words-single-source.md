# ADR-0001：我的单词与已掌握是两份独立列表

- 状态：**待批准**
- 日期：2026-11-22
- 相关：`specs/005`、`specs/013`、`ARCHITECTURE.md` §6

## 背景

2026-11-22 实测：用户有 15 条词汇收藏，其中 3 条同时 `word_states.mastered=1`（Affordability / intimately / thorny）。
App 顶栏用 `favorites − mastered` 得到 12；阅读页直接取收藏长度得到 15；单词本又各自推导。同一个事实出现多个数字。

历史原因：互斥规则 2026-11-22 才写入 specs/005；此前的“先收藏、后标掌握”是两次独立调用，服务端标记 mastered 时不删收藏。

## 决定

1. **我的单词 = `favorites`（type=vocabulary）列表本身**；计数 = 列表长度，由单一 selector 暴露。
2. **已掌握 = `word_states.mastered=1` 独立列表**；两者不允许重叠。
3. 互斥由**写路径**保证：标记已掌握时删除同词收藏（未来服务端同事务；当前前端命令 + 回滚）。
4. **禁止**任何 `favorites − mastered`、读时交集过滤或第二份本地镜像参与计数/导出。
5. 存量重叠是**数据缺陷**：一次性 reconcile（dry-run → 备份 → 审计 JSONL → 逐条删除 → 验收 0 重叠 → 可回滚），不改 `word_states`。
6. `unmarkMastered` 不自动回填收藏；用户需显式再收藏。

## 后果

- 修复后收藏数从 15 变 12，所有壳显示同一数字；已掌握 tab 仍显示这 3 个词。
- 导出使用 `selectMyWords()`，不再依赖运行时过滤。
- 必须补不变量测试与巡检脚本；未来任何消费方只读 selector。
- 删除收藏是有损操作 → 保留备份与回滚脚本，且不得静默批量执行。

## 被否决的方案

- **保留减法**：把数据缺陷固化成永久公式，新增消费方继续分叉。
- **读时过滤收藏**：让“我的单词”永远看不到真实列表，导出/计数继续不一致。
- **删 `word_states` 记录**：已掌握是用户学习状态，不能为修数字而丢。
- **前端 reconcile 静默批量删**：写操作必须可审计、可回滚、由集成者执行。
