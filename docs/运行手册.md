# 运行手册：备份 / 恢复 / 恢复演练

> 适用：语途（LinguaTrek）M1 ③（迁移框架 + 离机备份）的**备份部分**。
> 最后更新：2026-11-15。脚本与本文只覆盖数据面；不含应用代码、依赖安装与 systemd/Caddy 配置。

## 0. 一句话

```bash
# 备份（默认 data/ -> backups/，保留最近 7 份）
scripts/backup.sh

# 恢复到空目录（默认临时目录；目标目录 = 新的 data 根目录）
scripts/restore.sh backups/linguatrek-backup-YYYYmmdd-HHMMSS.tar.gz --to /tmp/restore-test

# 自动演练：备份 -> 临时恢复 -> 与源数据比对 -> 清理；PASS/FAIL + 退出码
scripts/restore_drill.sh
```

三个脚本都只用标准工具（`bash`、`sqlite3`、`tar`、`shasum`/`sha256sum`），面向 macOS 自带 bash 3.2 与 Linux 均可运行。

## 1. 脚本与数据位置

| 脚本 | 作用 | 关键行为 |
|---|---|---|
| `scripts/backup.sh` | 生成 `.tar.gz` 备份 | 优先 `sqlite3 .backup`（WAL 安全）；无 sqlite3 时退化为文件复制并警告；默认保留最近 7 份 |
| `scripts/restore.sh` | 从备份恢复并校验 | 先校验 `SHA256SUMS` + `PRAGMA integrity_check` + 表/用户/文件数 + 聚合哈希，全部通过后才写入目标；默认拒绝非空目标 |
| `scripts/restore_drill.sh` | 自动恢复演练 | 独立取源快照 → 备份 → 临时恢复 → 对比表/用户/文件/哈希 → 清理；输出 PASS/FAIL 与耗时 |

默认路径：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DATA_DIR` | `<repo>/data` | 数据根目录 |
| `AUTH_DB_PATH` | `$DATA_DIR/app.db` | SQLite 路径，优先级高于 `DATA_DIR` |
| `USER_DATA_DIR` | `$DATA_DIR/users` | 每用户数据根目录 |
| `BACKUP_ROOT` | `<repo>/backups` | 备份归档目录 |
| `BACKUP_KEEP` | `7` | 保留份数；`--keep N` 可覆盖 |
| `SQLITE3_BIN` | `sqlite3` | 可指向不存在以演练“无 sqlite3”的退化路径 |
| `ENV_FILE` | `<repo>/.env` | **只读取键名**，不复制值 |
| `ENV_EXAMPLE` | `<repo>/.env.example` | 作为模板复制进备份 |

> **VPS 上必须显式设 `DATA_DIR`**：脚本按自身位置推断仓库根；若把 `scripts/` 放进 release 目录，默认会指向 `release/data`，与持久卷 `/srv/ln/data` 不一致。示例见 §2.3。

## 2. 备份

### 2.1 内容

归档名：`linguatrek-backup-YYYYmmdd-HHMMSS.tar.gz`；解包后是一个同名目录：

```text
linguatrek-backup-YYYYmmdd-HHMMSS/
├── app.db                 # sqlite3 .backup 生成的快照（WAL 安全）
├── users/                 # USER_DATA_DIR 的完整复制
├── SHA256SUMS             # app.db / users/ 的逐文件 SHA256
├── manifest.env           # 快照元数据（表清单、用户数、文件数、聚合哈希、git commit…）
└── config/
    ├── env.keys           # .env 的“键名”清单（不含值）
    ├── env.example        # 配置模板
    └── README.txt
```

**不包含**：`.env` 的值、任何密钥、`history/`（旧版未登录回落目录）、`data/ecdict.db`（可重新下载的词典）、应用代码、日志、`subtitles/`。备份含邮箱、口令哈希与学习记录，属于个人数据，按 §5 管理。

### 2.2 一致性与降级

- 有 `sqlite3`：用 `.backup` 生成一致性快照，可在服务运行时执行；备份后立刻做 `PRAGMA integrity_check`。
- **没有 `sqlite3`**：退化为 `cp` 文件复制，并打印风险警告。此时 WAL 可能未合并，在线备份不保证一致；**建议先停服务再备份**，或安装 sqlite3 后重跑。恢复端仍会用 sqlite3 做完整性检查，因此坏包会在恢复时暴露。
- `users/` 是逐文件复制，不是事务快照。备份期间用户正在写 JSON 时，可能拿到半截文件；建议低峰执行，或停写后备份。若复制期间源文件数变化，脚本会提示。

### 2.3 命令与保留策略

```bash
# 默认：仓库 data/ -> 仓库 backups/，保留 7 份
scripts/backup.sh

# 保留最近 14 份
scripts/backup.sh --keep 14

# 自定路径（VPS 示例）
DATA_DIR=/srv/ln/data \
USER_DATA_DIR=/srv/ln/data/users \
BACKUP_ROOT=/srv/ln/backups \
/srv/ln/current/scripts/backup.sh
```

- 每次输出归档绝对路径、大小、内容摘要（表数/用户数/文件数），**不打印任何密钥**。
- 只清理 `BACKUP_ROOT` 下由本脚本命名的 `linguatrek-backup-*.tar.gz`；超过保留份数的从旧到新删除。不会碰其他文件。
- 同一秒内重复运行会等到下一秒，保持时间戳命名。
- 未指定 `USER_DATA_DIR` 时用 `DATA_DIR/users`；迁移过目录的部署请显式设置。

### 2.4 定时备份

**cron（Linux）**——cron 不加载登录 shell 的 PATH，务必显式写：

```cron
PATH=/usr/local/bin:/usr/bin:/bin
17 3 * * * cd /srv/ln/current && DATA_DIR=/srv/ln/data USER_DATA_DIR=/srv/ln/data/users BACKUP_ROOT=/srv/ln/backups ./scripts/backup.sh >> /var/log/linguatrek-backup.log 2>&1
```

**launchd（macOS）**——保存为 `~/Library/LaunchAgents/com.linguatrek.backup.plist`，把 `<repo>` 换成实际绝对路径：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>com.linguatrek.backup</string>
  <key>ProgramArguments</key>
  <array>
    <string>/bin/bash</string>
    <string>&lt;repo&gt;/scripts/backup.sh</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key><string>/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin</string>
    <key>DATA_DIR</key><string>&lt;repo&gt;/data</string>
    <key>BACKUP_ROOT</key><string>&lt;repo&gt;/backups</string>
  </dict>
  <key>StartCalendarInterval</key>
  <dict><key>Hour</key><integer>3</integer><key>Minute</key><integer>17</integer></dict>
  <key>StandardOutPath</key><string>/tmp/linguatrek-backup.log</string>
  <key>StandardErrorPath</key><string>/tmp/linguatrek-backup.err</string>
</dict>
</plist>
```

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.linguatrek.backup.plist
# 或旧系统：launchctl load ~/Library/LaunchAgents/com.linguatrek.backup.plist
```

不要并发跑两个备份；脚本没有加锁。cron 与手工操作错开。

### 2.5 异地存储（离机）

本脚本只负责本地归档；**离机是单独一步**，建议每天备份后同步到 R2/B2 等 S3 兼容存储：

```bash
# 用 copy 而不是 sync：远端保留更久的历史，本地保留策略不影响远端
rclone copy /srv/ln/backups r2:linguatrek-backup/ \
  --include 'linguatrek-backup-*.tar.gz' --checksum

# 抽查
rclone check /srv/ln/backups r2:linguatrek-backup/ \
  --include 'linguatrek-backup-*.tar.gz'
```

- **先加密再离机**（备份含 PII/口令哈希）。可用 `age`：
  ```bash
  age -r age1... -o /srv/ln/backups/linguatrek-backup-<stamp>.tar.gz.age \
      /srv/ln/backups/linguatrek-backup-<stamp>.tar.gz
  rclone copy /srv/ln/backups r2:linguatrek-backup/ --include '*.age' --checksum
  ```
  或直接使用 `rclone crypt` 远端；私钥/口令放密码管理器，**不要**放仓库。
- 对象存储配生命周期（如 30/90 天）；本地保留份数不等于离机保留份数。
- 备份缺失 > 24h 应告警（C20 的一部分；本手册不实现告警通道）。

## 3. 恢复

### 3.1 恢复前

1. **停服务**（SQLite 单写进程；恢复时不能有进程占用目标库）：
   ```bash
   sudo systemctl stop lingua-nova
   ```
2. 确认目标目录：`--to` 指向**新的 data 根目录**，恢复后其结构为 `app.db + users/ + backup-meta/`。
3. 查备份元数据，确认代码版本匹配：
   ```bash
   ARCHIVE=/srv/ln/backups/linguatrek-backup-YYYYmmdd-HHMMSS.tar.gz
   tar -xOzf "$ARCHIVE" "$(tar -tzf "$ARCHIVE" | grep 'manifest.env$' | head -1)"
   ```
   看 `GIT_COMMIT` / `ALEMBIC_VERSION` / 时间。应用代码应使用与备份相同或更新的 release；若代码更新，先按迁移流程升级（迁移前再备份一次）。
4. 磁盘留足空间（归档解压 + 新库 + 旧数据备份目录）。

### 3.2 命令

```bash
# 恢复到空目录（默认 mktemp 临时目录；打印路径）
scripts/restore.sh /srv/ln/backups/linguatrek-backup-20261115-031700.tar.gz

# 恢复到指定目录（目录必须不存在或为空）
scripts/restore.sh /srv/ln/backups/linguatrek-backup-20261115-031700.tar.gz \
  --to /srv/ln/data

# 覆盖已有数据目录：先把旧 app.db/users/backup-meta 移到 .pre-restore-<stamp>
scripts/restore.sh /srv/ln/backups/linguatrek-backup-20261115-031700.tar.gz \
  --to /srv/ln/data --force
```

- **默认拒绝非空目标**；`--force` 不是删除，旧数据被移进 `目标/.pre-restore-YYYYmmdd-HHMMSS/`，确认无误后再手工清理。
- 校验失败时不会写入目标；显式 `--to` 的空目录也不会被创建。自动创建的临时目标在失败时若为空会被删掉。
- 恢复后脚本会设置 `users/` 与 `backup-meta/` 为 0700、`app.db` 为 0600；文件属主需要按部署用户调整（见 §3.4）。
- 恢复完成后会在目标下生成 `backup-meta/`（manifest、SHA256SUMS、config/env.keys），它不参与应用运行，只供核对。

### 3.3 校验项（脚本自动执行，失败即非 0）

| 检查 | 说明 |
|---|---|
| `SHA256SUMS` | 归档内每个数据文件逐项比对；损坏/被改动的包在这里被挡住 |
| `PRAGMA integrity_check` | 必须为 `ok`；坏页、截断、非 SQLite 文件都会失败 |
| 表清单 | 与 `manifest.env` 的 `TABLE_COUNT` / `TABLES` 一致 |
| 用户数 | `SELECT count(*) FROM users` 与快照一致 |
| `data/users` 文件数 | 与快照一致 |
| users 聚合 SHA256 | 相对路径 + 内容的聚合哈希与快照一致 |
| `alembic_version` | 不一致仅打印 WARN（备份与代码版本的提示，不单独判失败） |

成功输出示例（实际数字随数据变化）：

```text
[restore] [PASS] 文件哈希：11 个数据文件通过（SHA256SUMS）
[restore] [PASS] PRAGMA integrity_check：ok
[restore] [PASS] 表数量：6
[restore] [PASS] users 表存在：1
[restore] [PASS] 用户数：3
[restore] [PASS] data/users 文件数：10
[restore] [PASS] users 聚合 SHA256：…
[restore] 恢复结果：PASS
```

### 3.4 空机器恢复（从离机备份到新机）

1. 安装同版本应用代码与依赖，准备数据目录 `/srv/ln/data`（属主为运行用户）。
2. 从对象存储取回**加密包**，解密后按 §3.2 恢复到 `/srv/ln/data`。
3. 恢复环境变量：`.env` **不在备份里**；按 `backup-meta/config/env.keys` 的键名，从密码管理器重新填写值。不要从旧机拷明文的 `.env` 到不安全位置。
4. 权限：
   ```bash
   sudo chown -R ln:ln /srv/ln/data
   sudo chmod 700 /srv/ln/data/users /srv/ln/data/backup-meta
   sudo chmod 600 /srv/ln/data/app.db
   ```
5. 启动服务，检查：
   ```bash
   sudo systemctl start lingua-nova
   curl -fsS http://127.0.0.1:8000/healthz
   sqlite3 /srv/ln/data/app.db 'PRAGMA integrity_check;'   # 期望 ok
   ```
6. 用旧账号登录，确认历史/收藏/订阅存在。确认无误后再删除 `.pre-restore-*`。

## 4. 恢复演练

### 4.1 命令与输出

```bash
# 用当前仓库 data/ 演练（低峰；源库只读查询，不启动服务、不占 8000）
scripts/restore_drill.sh

# 指定假数据目录自测（不碰真实 data/）
scripts/restore_drill.sh --data-dir /tmp/linguatrek-fake/data

# 失败后保留临时目录：路径会打印在 FAIL 行下方
scripts/restore_drill.sh --keep-temp
```

成功输出：

```text
[1/4] 备份 ... OK（linguatrek-backup-20261115-054621.tar.gz）
[2/4] 恢复到临时目录 ... OK
[restore] [PASS] 文件哈希：11 个数据文件通过（SHA256SUMS）
[restore] [PASS] PRAGMA integrity_check：ok
[restore] [PASS] 表数量：6
[restore] [PASS] 用户数：3
[restore] [PASS] data/users 文件数：10
[3/4] 校验源数据与恢复结果 ... OK（表 6、用户 3、文件 10、users 哈希一致）
[4/4] 清理临时目录 ... OK
PASS 恢复演练通过：表 6、用户 3、文件 10、users 哈希一致；耗时 1s
```

- 退出码：`0` = PASS；非 0 = FAIL。
- 脚本自己创建临时备份根目录并在成功/失败后清理（`--keep-temp` 除外），不会污染仓库 `backups/`。
- 源数据在备份后发生变化会导致比对失败——这是预期行为；低峰/停写后重跑。

### 4.2 频率（建议）

| 频率 | 做什么 |
|---|---|
| **每周** | 本机自动/人工跑一次 `restore_drill.sh`（低峰），确认备份可恢复且计数一致 |
| **每季** | 从**离机备份**恢复到一台空机/临时目录，按 §3.4 走一遍登录与历史检查（这是 S21 的硬要求） |
| **每次迁移前** | 先 `backup.sh`，再迁移；迁移后用副本演练一次 |
| **变更后** | 改 `DATA_DIR`/`USER_DATA_DIR`/存储位置、升级 SQLite/系统后立即演练 |

M1 验收至少要在本机/staging 成功完成一次“从备份恢复到空目录”的演练（Gate-0 ④）。**2026-11-15 已用真实数据副本在本机完成（§4.5）；空机/异地恢复待做。** 连续两次演练失败，或备份缺失 > 24h 时，按项目风险登记 R5/R6 停发版修链路。

### 4.3 故意损坏包（验证 FAIL）

```bash
# 截断归档：应在解压/读取阶段失败
head -c 500 backups/linguatrek-backup-20261115-054629.tar.gz > /tmp/corrupt.tar.gz
scripts/restore.sh /tmp/corrupt.tar.gz --to /tmp/restore-corrupt
echo $?   # 非 0（当前实现为 1）
```

也可保留合法 tar 但改动其中 `app.db`，恢复会在 `SHA256SUMS` 阶段失败。两类失败都不会写入目标目录。

### 4.4 演练自测（不碰真实 data/）

```bash
FAKE=$(mktemp -d /tmp/linguatrek-fake.XXXXXX)
mkdir -p "$FAKE/data/users/u1"
sqlite3 "$FAKE/data/app.db" <<'SQL'
CREATE TABLE users (id TEXT PRIMARY KEY, email TEXT UNIQUE NOT NULL);
CREATE TABLE sessions (token_hash TEXT PRIMARY KEY);
INSERT INTO users VALUES ('u1', 'u1@example.test');
SQL
printf '{}\n' > "$FAKE/data/users/u1/favorites.json"
scripts/restore_drill.sh --data-dir "$FAKE/data"
rm -rf "$FAKE"
```

- 抽查 `users/581d…`（9 个文件，含 `history/vi-VN/`）与 `users/4351…`（1 个文件）：文件数与内容聚合哈希均与源副本一致。

## 5. 注意事项

- **密钥不入备份**：脚本只保存 `.env` 的键名与 `.env.example`；恢复后必须人工重新配置值。日志/输出不打印密钥。
- **备份是 PII**：含邮箱、口令哈希、学习记录。归档默认 `umask 077`；目录与归档应仅属主可读；离机前加密。
- **异地存储**：本地 `backups/` 与对象存储是两层；只做本地等于没有离机保护。建议 3-2-1（本机 + 对象存储 + 至少一份离线/异账号）。
- **保留期与删除权**：默认 7 份；按隐私政策调整。被删除用户的数据仍会存在于旧备份中，直到对应备份过期；不要把保留期设得超过承诺。
- **目标非空**：不要为了省事直接 `--force` 覆盖生产目录；先确认 `.pre-restore-*` 有旧数据，恢复并登录验证后再删。
- **恢复时停写**：应用进程、sqlite3 CLI、备份任务都不要同时碰目标 `app.db`；WAL 侧文件不要手工留下旧的 `-wal`/`-shm`。
- **脚本不启动/停止服务**：恢复与演练都不碰 8000；上线/回滚仍走 systemd。
- **路径**：`AUTH_DB_PATH`/`USER_DATA_DIR` 可用绝对路径覆盖；迁移过数据目录的部署务必显式设置，不要依赖默认值。
- **`backups/` 目前未加入 `.gitignore`**（本任务按“只新增脚本/文档”约束未改 `.gitignore`）。不要把备份 `git add`；建议后续在 `.gitignore` 加 `/backups/`。
- **`restore_drill.sh` 的源库只读查询**可能为 WAL 库生成短暂的 `-shm`；这是 SQLite 正常行为，不会改业务数据。演练期间仍建议停写，避免比对误报。

## 6. 已知风险与残余风险

> 这里只列「明确知道、当前版本不修」的风险；修复后请删掉对应条目，并在计划书 M1 进度里记一笔。日常备份/恢复风险见 §5。

| 风险 | 现状 | 影响 | 缓解 / 升级条件 |
|---|---|---|---|
| 后台独立角色 + 2FA | 后台止血台只有 `ADMIN_EMAILS` 邮箱白名单（环境变量），没有独立 role 表/2FA/操作审计 | 拿到管理员邮箱对应的账号即可看全部运营快照；没有二次确认 | 止血台**只读**（无删除/改数据动作），泄露面仅统计与邮箱；独立 role + 2FA + 审计日志仍须在 M5 急救动作上线前补齐 |
| 审计日志 | 只有结构化访问日志（method/path/status/user_id），没有操作审计 | 无法追溯「谁在何时改了什么、删了什么」 | 后台动作上线前补 append-only 审计表（操作人、动作、对象、时间、结果） |
| 提示注入 | 字幕/视频文本会进 LLM prompt；尚无「内容与指令分离」和输出 schema 白名单 | 恶意字幕可能诱导模型输出异常 JSON 或指令性内容 | 现有输出经 JSON 解析 + 按 id 对齐校验，失败会重试/标未翻译；后续加内容/指令隔离、禁工具调用、单请求 token 上限 |
| 域名解析黑名单 | 未单独实现（按设计不加） | 无直接暴露 | 见 [backend/README「抓取边界」](../backend/README.md)：出站目标由代码派生（锚定 YouTube host / 规范 URL），频道 URL 也先过 YouTube 频道白名单，没有任意 URL 抓取路径；以后新增任意 URL 功能时必须补 scheme/host 白名单 + 解析后 IP 黑名单 |
| WAF / bot 指纹 / IP 信誉库 / 渗透测试 | 不做 | 无法识别分布式或真人模拟攻击 | 计划书显式接受；对冲 = 日预算硬闸 + 限速 + 登录锁定；上线 30 天内出现 2 次以上批量薅取，升级为专项（5–8 人日） |
| 限速/锁定只在单进程内存 | 多 worker 各算各的；反代后 `request.client.host` 可能是代理 IP | 多 worker/反代下实际阈值被放大 | MVP 默认单进程；多 worker 部署需在反代层做 IP 限速，或后续换共享存储 |
| 抓取上限的边界 | `requests` timeout 是连接/读取超时；`MAX_FETCH_BYTES` 不覆盖 yt-dlp 元数据/频道 HTML | 极端慢速 drip / 超大 HTML 仍可能占用线程 | 15s 超时 + `extract_flat` 小响应；后续可加整体 deadline/进程级超时 |
| 登录锁定的可用性 | 攻击者可用任意邮箱打满阈值（账号锁定不区分存在性） | 可能对特定邮箱造成 15 分钟拒绝登录 | 锁定只影响新的登录、不影响已有 Cookie；阈值/时长可调（`AUTH_LOCK_*`）；后续可加验证码/邮箱验证 |

其他功能/合规残余项：

- **游客态未实现**：所有数据仍绑定登录用户；旧 `history/` 迁移见 §5。
- **备份未自动离机**：`scripts/backup.sh` 只落本地 `backups/`；异地 rclone 仍是手册步骤，未接 cron。
- **删除权**：删除用户后旧备份仍保留到对应备份过期；表级删除矩阵未落地。
- **AI 内容标识**：翻译/总结尚未加显式 AI 标识（P0 合规项，见计划书）。
- **邮件通道**：无 SMTP/SPF/DKIM/DMARC，忘记密码/邮箱验证/事务性邮件无法上线。

## 7. 故障速查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `找不到数据库` | `DATA_DIR`/`AUTH_DB_PATH` 不对；release 目录不是仓库根 | 显式设 `DATA_DIR`；确认 `app.db` 在持久卷 |
| `未找到 sqlite3，退化为文件复制` | PATH 缺 sqlite3 | 安装 sqlite3 后重跑；或停服后再备份 |
| `目标目录非空` | 目标已有数据 | 换空目录；确认覆盖用 `--force`（旧数据会移到 `.pre-restore-*`） |
| `文件哈希校验失败` | 归档损坏/被改动/传输截断 | 换一份备份；检查 rclone 校验；不要手工改包内文件 |
| `integrity_check 未通过` | 备份时库已损坏/文件复制不一致 | 用更早的备份；检查磁盘与 WAL；恢复前不要继续写 |
| `users 文件数/哈希不一致` | 备份期间用户数据在变；恢复复制不完整 | 停写后重做备份；检查磁盘空间 |
| `PASS` 但登录失败 | `.env` 未配置、代码版本不匹配、属主不对 | 按 `backup-meta/env.keys` 配环境；核对 `GIT_COMMIT`/`ALEMBIC_VERSION`；`chown` |
| 演练总在比对处失败 | 源数据在演练期间有写入 | 低峰/停写后重跑；或用一份静态副本 |
| 备份目录增长过快 | 保留份数太大、用户文件大 | 调 `--keep`；离机后本地可减少；监控磁盘 |
| `backups/.staging/` 残留 | 备份进程被 `kill -9`/断电 | 确认没有并发备份后删除该目录；正常失败会自动清理 |

## 8. 后台管理员配置与止血流程

> 适用：M1 ⑥ 后台止血台（用户需求 #12）。实现与端点契约见
> [backend/README「后台止血台」](../backend/README.md) 与
> [specs/021-admin](../specs/021-admin/spec.md)。这里只讲**配置**与**出事时怎么用**。

### 8.1 配置管理员（环境变量，不写库）

```bash
# .env（不要提交；改完重启后端才生效）
ADMIN_EMAILS=alice@example.com,bob@example.com
```

- 逗号分隔、大小写不敏感；空值/不设置 = **没有管理员**（所有 `/api/admin/*`
  对任何登录用户都 403）。
- 只读 `config.ADMIN_EMAILS`，**不建 role 表、不新增迁移**；管理员账号仍然
  走正常注册/登录。
- 验证：登录后 `GET /api/auth/me` 应返回顶层 `"isAdmin": true`；前端顶栏会
  出现「止血台 / Bảng điều hành」按钮。普通用户访问任一 `/api/admin/*` 为
  **403**；未登录为 **401**。
- 不要把 `ADMIN_EMAILS` 写进前端 `VITE_*`、提交到仓库或贴进日志；它只是邮箱，
  但泄露名单会缩小撞库目标。

```bash
# 临时实例（不影响仓库 data/）
cd backend
ADMIN_EMAILS=admin@example.com DATA_DIR=/tmp/ln-admin/data \
  AUTH_DB_PATH=/tmp/ln-admin/data/app.db \
  venv/bin/uvicorn main:app --port 8001
```

### 8.2 页面与端点

| 页面区域 | 对应端点 | 先看什么 |
|---|---|---|
| 总览卡片 | `GET /api/admin/stats` | 用户总数/今日活跃/今日花费/失败任务 |
| 7 天用量 | `GET /api/admin/usage?days=7` | 哪个功能在烧钱、哪天异常 |
| 用户表 | `GET /api/admin/users?limit=50&search=` | 最近注册、单用户本月花费、最后活跃 |
| 健康与错误 | `GET /api/admin/health` | DB/迁移、`data/` 占用、最近 10 条 failed jobs |

- 限速：`/api/admin/*` 每登录用户 **30 次/分钟**（`RATE_LIMIT_ADMIN_PER_MINUTE`，
  0 关闭），超限 429 + `Retry-After`；页面一次刷新会打 4 个请求。
- 所有数字都是**估算/聚合**，不是账单：AI 花费来自 `ai_usage.est_cost_usd`
  （未知价格按已知最贵计），与厂商后台可能对不上；以账本趋势为准。

### 8.3 止血流程（只读台能做什么、不能做什么）

1. **先看健康**：`health.status=degraded` 时看 `db.ok`、
   `db.migrations.current/head`、`disk.sizeBytes`。迁移落后就按
   [migrations/README](../backend/migrations/README.md) `alembic upgrade head`；
   磁盘将满先做备份/清理旧备份，不要删 `data/users/` 或 `app.db`。
2. **再看花钱**：今日/本月花费 + `todayByFeature`。某功能突然放大时，先用
   `/api/admin/users` 找当月花费最高的用户，再对照 `usage` 看是哪一天/哪个功能；
   确认异常后在**台外**处置（如临时下调 `AI_DAILY_BUDGET_GLOBAL_USD` /
   `AI_DAILY_QUOTA_*`、换 Key、停用问题模型）——止血台没有改配置/封号/退款按钮。
3. **失败任务**：`jobs.failed` 与 `health.failedJobs`。看 `error` 与
   `kind/contentRef` 判断是字幕缺失、provider 429 还是数据损坏；当前 M1 的
   job 只能由用户重新发起来续传（`partial/queued` 属于 `pendingRetry`），
   止血台不提供重试/删除。
4. **用户异常**：今日活跃骤降先看是否 DB/迁移/服务本身问题；某邮箱可疑时用
   搜索 + 本月花费 + 事件数评估，需要封禁/退款走 M5 的急救动作（尚未实现）。
5. **收尾留痕**：当前没有操作审计（因为没有任何写操作）。如果你在台外执行了
   改配置/换 Key，请记录时间、操作人、命令与 index；后续补审计表。

### 8.4 已知边界

- 管理员身份只靠环境变量：没有独立 role、2FA、操作审计；不要共用管理员邮箱。
- 只读：没有删除用户/内容、封号、退款/补偿、开关切换；这些是 M5 的 4 个急救
  动作，本规格明确不做。
- 旧库没跑迁移时统计字段降级为 0/空（页面仍能打开）；`health` 会显示真实
  degraded 原因。
- 单进程限速：多 worker 各算各的；公网部署仍应在反代层加 IP 限速。
- 统计读的是主库：大表 `learning_events` 上的「事件数/最后活跃」在用户量大时
  会变慢；M1 容量假设 ≤1,000 MAU，超过再迁 Postgres/加汇总表。
