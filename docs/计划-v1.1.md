## 1. 全局裁决（先定这些，否则逐项反复）

### 1.1 命名：新功能叫「观影模式」

仓库里「沉浸」已被占用：[信息架构-导航重构.md:473](信息架构-导航重构.md#L473) 的「学习页要沉浸」= **隐藏底部导航栏**（`App.tsx:260` 的 immersive task views）。v1.1 第 1 项是**播放态沉浸**，同名会互相污染。

- 新功能：**观影模式**（内部 `watchMode`，key `yt_bilingual_watch_mode`）
- 既有的：**全幅布局**（只改名，不改代码）

### 1.2 观影模式本身不许新增 AI 调用

词条窗必须是**已有教学分析（specs/028）的另一种呈现**：
- 数据源：`GET /api/teaching-analysis/{content_ref}` 或视频处理时合并进字幕缓存的 payload（`teaching_analysis.py:922-990`）
- 缓存键 `content_hash × level × target_lang × analysis_version`，命中零调用零扣费（`teaching_analysis.py:771-794`）

**任何「逐句实时问模型」的方案一律否决**——那是每片几十次调用，直接吃光配额。

### 1.3 必须先修的一个数据一致性问题（横跨任务 1、4）

教学分析有两条读取路径：
1. 全局表 `content_teaching_analysis`（无 `user_id`）→ 端点登录才可读（`routes_teaching_analysis.py:52-56`）
2. **合并进 per-user history JSON**（`teaching_analysis.py:922-957`）→ 随 payload 直接下发，游客也能读到

结果：同一份数据，一条路要登录、一条路不要。观影模式和游客开放都会踩这个坑，**必须先统一**（建议：只走全局表端点，不再合并进 per-user payload；合并逻辑保留给写缓存）。

### 1.4 事件先埋，不要上线再补

新增行为必须新埋事件，**日志不可回填**。v1.1 至少要定这几个名字：`watch_mode_toggle`、`gloss_panel_open`、`word_mastered`、`word_source_click`。

### 1.5 发布纪律（不变）

本地迭代，**不自动部署**。线上仍跑 `41c463b`；`280fb9b`（桌面端测试报告修复）等 3 个提交未上线，且 `280fb9b` 的 UI 改动**未在浏览器实测**。v1.1 任何一项都不改变这条纪律。

### 3.2 六个子项与做法

**2a「我已掌握」词表**
- 裁决：**建在 `word_states.mastered`**，不做成收藏的一个 type。理由：任务 3（标亮过滤）与任务 9（复习）都要读它；放 favorites 会有两处真相
- SQLite `CHECK` 约束需**重建表**迁移
- 交互：所有词表（收藏 / 内置词表 / 搜索结果）每词都有「我已掌握」；标记后从收藏移出、进「已掌握」词表；可撤销

**2b 见过次数（视频 + 阅读）**
- 数据源 `dict_lookup` 已够，但 60s 去重、不传 lemma → 同词不同形态会分开计
- 做法：事件补 `lemma` + `source_ref`，再建**物化表** `word_seen(user_id, word, seen_count, last_seen_at, last_source_ref, last_source_kind)`
- 我建议物化表而非实时聚合：排序要在 SQL 里做，实时聚合每次翻页都扫事件表

**2c 来源显示最后一次见的链接，取消原句**
- 依赖 `last_source_ref`
- 展示：来源图标（视频/文章/书）+ 标题 + 可点跳转（回到那一秒 / 那一段）
- 老收藏里的 `context_en` **不删数据**，只是不再展示（复习可能要用）

**2d 统一"加入时的解释来源"**
- 现状 `zh_text = ipa + 首义` 是拼出来的字符串，不是结构化释义
- **推荐存指针**：只存 `word`，渲染时查 `dictionary_cache.json`（零冗余、改一次全站生效）
- 明确不存上下文释义（你已指定）

**2e 筛选与排序**
- 排序：加入时间 / 难度 / 见过次数；筛选：类型（词/短语）、来源、未掌握
- 难度排序需每词档位 → 前端批量查 `/api/vocabulary/level`（已有），或在 `word_seen` 冗余 `cefr`

**2f 内置词表存完整解释 + 溢出折叠**
- 现状只有 `phonetic + translation`（`lexicon.v1.json` 1.1MB / 10k 词）
- 可用资产：本地 `data/ecdict.db`（104MB，有 `definition` 英文释义列）
- 做法：改词表生成脚本，带入 `definition` + `translation` + 词性；前端默认两行、溢出折叠
- 体积：预计 2–3 倍（约 2–3MB），需先量

### 3.3 最小版（4–6 人日）

1. `word_states` 加 `mastered`（迁移 + 重建表）
2. `favorites.json` 加 `last_source_ref / last_source_kind`，渲染来源链接、不显示原句
3. 「我的单词」加排序（加入时间 / 见过次数），见过次数先实时聚合事件
4. 「我已掌握」按钮与词表

### 3.4 完整版（+4–6 人日）

5. `word_seen` 物化表 + 事件补 lemma/source_ref + 排序走 SQL
6. 收藏指针化（渲染时查词典缓存），老数据兼容
7. 内置词表完整释义 + 折叠
8. 全量筛选（类型/来源/未掌握/难度）

### 3.5 风险（都很硬）

1. **不要改 `_favorite_fingerprint` 输入**——会让无 id 老收藏 id 漂移，旧收藏失联
2. 收藏**没有 `target_lang`**，迁到 `word_states` 会把义项错标语言

## 8. 任务 7 · 存储规范与用户总量限制

### 8.1 现状

| 事实 | 证据 |
|---|---|
| **没有任何单用户存储总量配额**，唯一例外是本地 EPUB：20 本 / 100MB | `config.py:619-638`；`routes_book_upload.py:134-154` |
| 视频 history、reading、导入公版书、quiz、课程**都无上限** | 各路由无总量检查 |
| **游客目录完全没有清理**：本机开发库已有 **6753 个**游客目录 | `data/guests` 实测 |
| 导出限 200MB / 24h / 3 次每 30 天 | `account_export.py:51-53, 285-294` |

### 8.2 做法：先量后限，分类治理

**第一步 · 量（0.5 人日，必须先做）**
只读脚本：按 `user_id` 聚合各表占用 + `du` 各目录，输出 P50/P90/P99。**阈值由真实分布决定，不拍脑袋定 100MB**。

**第二步 · 分类**

| 类别 | 内容 | 策略 |
|---|---|---|
| 可重建缓存 | 字幕 payload、翻译、教学分析、题目 | **不设硬配额**，按「30 天未访问 + LRU」淘汰；全局缓存先去重 |
| 用户产物 | 收藏、生词、书籍上传、进度、课程尝试 | 设总量配额 + 提前提示；EPUB 已有 |
| 游客目录 | `data/guests/*` | **TTL 7 天 + 数量上限 + 定时清理**（现在一条都没有） |

**第三步 · 机制**
- 清理任务挂既有 cron/心跳，每日跑
- 超限时**先清可重建缓存，而不是拒绝写入**（拒绝写入会让用户以为产品坏了）
- **不可重建的用户数据只提示、绝不自动删除**（删除不可逆，红线）

### 8.3 风险

1. 删用户可见数据不可逆 → 只自动清可重建类
2. 「可重建」判定错等于删数据 → 判定表人工复核并写进 spec
3. 淘汰缓存会让二次打开变慢或重新花钱 → 淘汰前确认全局缓存还在
4. 游客 TTL 会打断「用几天再注册」→ TTL 与认领逻辑对齐（先认领再清理）
