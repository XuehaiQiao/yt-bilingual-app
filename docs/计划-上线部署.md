## 0. 一页结论

| 项目 | 结论 |
|---|---|
| **推荐组合（长期）** | **单台海外 VPS（Hetzner CX22 级，2 vCPU / 4 GB）+ Caddy 同域反代（`/` 静态、`/api` 反代）+ uvicorn 单进程 + SQLite WAL + 每日离机备份** |
| **推荐组合（首周灰度）** | **Railway 单容器 + Volume 挂 `/data`**（零运维、无平台级 SSE 超时），验证账号与长连接后再迁 VPS |
| **前端托管** | **同域静态**（Caddy 直接服务 `frontend/dist`）。**不要**把前端单独放 Vercel/Netlify——跨站 Cookie 在 Safari 默认被拦，登录态会莫名失效 |
| **数据库** | 认证库 `data/app.db` 与用户文件 `data/users/<id>/` 同放持久卷；**单写进程**、WAL、`busy_timeout` |
| **上线门槛（P0）** | 先决 3 件事：①事件循环里的同步调用（并发会互相卡死）；②SSE 缺心跳（代理 100s 空闲即断）；③`API_AUTH_KEY` 与浏览器会话互斥（设了它，登录也会 401；塞进前端又等于公开密钥） |
| **必做配置项** | **22 项**（C01–C22，见 §3） |
| **节奏** | M1 最小可用 2–3 天；M2 多用户（认证已落地，做验收与加固）1 周；M3 运营持续 |
| **月成本量级** | 基础设施 ≈ $5–8（VPS + 备份对象存储 + 域名摊销）；模型费用按用量，约 $0.1/90 分钟视频（按目录标价估算，见 §9.2） |

> 一句话：**同域、单进程、持久卷、有心跳、有离机备份**。先别追求「多副本/免费额度」，这个应用的瓶颈是 SSE 长连接和 SQLite，不是流量。

### 1.2 现有部署开关（当前代码已支持）

- `HISTORY_DIR` / `SUBTITLES_DIR` / `SENTENCES_DIR`：回落数据目录 / 本地剧集 / 句子精背（`backend/config.py:14-25`）。`HISTORY_DIR` 在 **import 时** 就 `makedirs`，容器里卷没挂好会直接启动失败。
- `DATA_DIR` → `AUTH_DB_PATH`（默认 `data/app.db`）、`USER_DATA_DIR`（默认 `data/users`）（`config.py:27-32`）。三者只需覆盖 `DATA_DIR` 就能整体挪到持久卷。
- `COOKIE_SECURE`：设为 `1/true/yes/on` 时 `ln_session` 加 `Secure`（`config.py:45-47`）；`SESSION_MAX_AGE` 是**代码常量 30 天**，当前不能用环境变量改。
- `CORS_ORIGINS`：逗号分隔白名单；空 = `*`（`config.py:37-38`）。
- `API_AUTH_KEY`：设置后所有 `/api` 必须带 `X-API-Key`（`main.py:63-78`；`.env.example` 已注明它是在会话之上的**额外**门禁）。**与浏览器登录互斥**，见 P0‑3。
- `LOCAL_DICT_PATH`：本地词典路径（`backend/local_dict.py:34,91`）。
- `GET /health`：唯一健康端点，公开（`main.py:97`）。
- `start_app.command` 的公网隧道（`ENABLE_TUNNEL=1` + `API_AUTH_KEY`）：**仅本机演示**，正文不把它当部署方案（`start_app.command:37-50`）。

> `.env` 加载路径固定为仓库根 `.env`（`config.py:10`，`load_dotenv` 默认不覆盖已有环境变量）。线上**不要**放 `.env` 文件，用 systemd `EnvironmentFile` 或平台环境变量；`.env` 已在 `.gitignore`，但 **Docker 构建上下文不受 `.gitignore` 约束**（见 §5.1）。

### 1.4 认证现状与上线前必须确认的点（18:20 快照）

> 认证前后端都已在工作区（后端 `auth_db.py` / `routes_auth.py` / `storage.py`；前端 `components/AuthScreen.tsx`、`lib/auth.tsx`），仍在开发中；下面是按**实际实现**列的契约与待办，行号漂移时以符号名为准。

**端点**（`routes_auth.py`，字段与状态码是冻结契约）：

| 方法 | 路径 | 成功 | 失败 |
|---|---|---|---|
| POST | `/api/auth/signup` | 201 + `Set-Cookie`（注册即登录） | 409 邮箱已存在 / 400 参数不合法 |
| POST | `/api/auth/login` | 200 + `Set-Cookie` | 401 统一"邮箱或密码错误"；429 限流 |
| POST | `/api/auth/logout` | 200 + 清 Cookie（不要求已登录） | — |
| GET | `/api/auth/me` | 200 + 当前用户 | 401 `{"detail":"未登录"}` |

**鉴权范围**：`/api/auth/*` 公开（由路由自己判）；其余 `/api/*` 未登录 401；`/health` 公开；OPTIONS 预检放行。

**前端**：`lib/auth.tsx` 启动时 `GET /api/auth/me` 决定显示 `AuthScreen` 还是应用；`apiFetch` 带 `credentials: 'include'`，业务端点 401 自动回登录页（`/api/auth/*` 的 401 不触发，避免登录页死循环）。验收要覆盖：未登录直达 → 认证页；登录后刷新保持；登出回认证页。

**Cookie**：`ln_session`；`HttpOnly`、`SameSite=Lax`、`Path=/`、30 天；`Secure` 由 `COOKIE_SECURE` 控制。服务端只存 **token 的 sha256**（`auth_db.py:5-6,53-55`），登录新建会话（**不吊销旧会话**），登出删当前会话；过期会话在登录/取会话时顺带清理（`auth_db.py:210-260`）。

**密码**：Argon2id（`argon2-cffi`，`auth_db.py:26,39`），密码 ≥8 位；账号不存在与密码错误返回同一 401，不泄露账号状态。

**存储**：`storage.py` 用 ContextVar 提供 `USER_DATA_DIR/<id>/{history,favorites,subscriptions}`；视频缓存、收藏、订阅、词典缓存都已切到 `storage.*`；未登录回落 `config.HISTORY_DIR`；`SUBTITLES_DIR` 保持共享只读。隔离要靠 §4 M2 的越权测试证明，**不要**假设改完就天然成立。

**环境变量**（已实现）：`DATA_DIR`、`AUTH_DB_PATH`、`USER_DATA_DIR`、`COOKIE_SECURE`。**未实现**：`SECRET_KEY`（opaque token 不需要）、`SESSION_TTL_DAYS`（固定 30 天）、`REGISTRATION_OPEN`（建议补）、邮箱相关配置。

**已知待办（上线前定夺）**：

1. **`API_AUTH_KEY` 冲突**（P0‑3）：key 中间件覆盖 `/api/auth/*`。公网多用户推荐「不设 key」；若坚持要 key，仅豁免 auth 端点还不够（其他 `/api` 仍要 key），需把浏览器端点整体排除在外——等于两套鉴权分支，不推荐（评审后再做）。
2. **注册开关/邀请码**：当前任何人可注册、注册即登录；至少加 `REGISTRATION_OPEN` 或网关层白名单。
3. **账号找回/验证**：没有。上线公告必须写明；M3 补邮件。
4. **会话吊销**：没有改密/踢下线入口（`delete_user_sessions` 未接线）；建议 M2 加「退出全部设备」。
5. **CSRF**：目前仅 SameSite=Lax；建议对 POST/PUT/DELETE 校验 `Origin` 同源。
6. **登录限流**：10 次/60s/IP、内存实现；网关再限一层，并确保反代后能拿到真实 IP。
7. **旧数据迁移**：v1 决策「旧 `history/` 不自动迁入新用户」。上线时归档或管理员手动导入，别把旧目录落进某个真实用户的数据根。

## 2. 托管方案对比

### 2.1 候选组合

| 代号 | 组合 | 说明 |
|---|---|---|
| **A** | **VPS + Caddy 同域** | Hetzner/DigitalOcean/Vultr，Caddy 终止 TLS 并反代，`frontend/dist` 由 Caddy 直接服务；单进程 uvicorn + 本地 SQLite |
| **B** | **Railway 单容器 + Volume** | Docker 多阶段（前端构建 + 运行时），Volume 挂 `/data`；单副本；平台给域名/TLS |
| **C** | **Render Docker + Starter + 磁盘** | 结构同 B，Render 托管；磁盘会禁用零停机部署 |
| **D** | **Fly.io Machine + Volume** | 需 Dockerfile + `fly.toml`；单机卷；无免费层 |
| E | 前端 Vercel/Netlify + 后端 B/C/D | 前后端不同站；需要 `SameSite=None; Secure` 与精确 CORS；**Safari 默认拦第三方 Cookie** |
| F | 平台 + Turso/Neon 替代 SQLite | 要改存储层（无 ORM，`sqlite3` 直连），只作为 M3 容量方案评估 |

### 2.2 对比表（核对日 2026-11-13，来源见 §9.3）

| 维度 | A · VPS + Caddy | B · Railway | C · Render | D · Fly.io | E · 前端 Vercel/Netlify |
|---|---|---|---|---|---|

### 2.3 SSE 与长请求：平台超时事实 + 配置建议

**事实**（外部信息，2026-11-13 核对）：

- **Cloudflare 代理**：默认 **100 秒 Proxy Read Timeout**，超时返回 524（官方 524 文档）。SSE 每次收到数据会刷新计时，所以**心跳 15–25s 就能保住**；否则把记录设为 **DNS only**（灰云）绕过。
- **Nginx**：`proxy_read_timeout` 默认 **60s** → 翻长视频必断；必须显式拉长并关缓冲。
- **Caddy**：默认按内容类型 flush，SSE 建议 `flush_interval -1`；`read_timeout` 默认足够，显式设 `24h` 更稳。
- **Render**：HTTP 响应最长约 100 分钟（官方文章）；免费实例 15 分钟无入站流量会休眠（正在进行的 SSE 算入站流量，但机器仍可能被重启）。
- **Railway**：未见平台级请求超时文档；以 30 分钟实测为准。
- **Fly.io**：官方社区称 60s 空闲超时已移除；仍需实测，并设 `min_machines_running = 1`。
- **Vercel/Netlify**：函数型运行时有硬上限（Vercel Hobby 300s；Netlify 同步 60s、后台 15 分钟）——**不要**用它们承载流式翻译。

**本项目的时间量级**（按代码参数估算）：

```
90 分钟视频 ≈ 900 个句子块（20 句/批）≈ 45 批
每批：LLM 8–40s + 批间间隔 4s（Gemini）/ 1s（DeepSeek）
单流总时长 ≈ 10–30 分钟
最坏空闲：429 退避 30–60s + 单批 40s ≈ 100s → 正好踩 Cloudflare 100s 线
```

**配置建议（缺一不可）**：

1. 后端每 **15s** 发一行 SSE 注释：`: ping\n\n`（浏览器自动忽略，但代理会计为数据）。这是 P0‑2。
2. Nginx：`proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s; proxy_send_timeout 3600s;`；Caddy：`flush_interval -1` + `transport http { read_timeout 24h }`。
3. 单流上限 **45 分钟**：超过则服务端主动结束并保留已翻译批次（现有落盘/自愈机制本就支持续译），前端提示「已保存 N 批，刷新可继续」。
4. 前端断流要能恢复：现在 `App.tsx` 用 `streamAbortRef` + `apiFetch` 读流（401 会自动回登录页），但断流后应自动重开同一 URL（缓存命中会立即回放已翻译部分并继续补译），否则用户只能手动刷新。
5. 模型调用：每批 **120s 超时**（Gemini SDK 的 `http_options` / DeepSeek 的 `httpx timeout=120`），失败按 15/30/60s 退避、最多 3 次，仍失败则把该批标 `[未翻译]` 继续下一批（现有自愈逻辑会补）；**不要**让单批无限挂起。
6. 外部抓取：yt-dlp 设 `socket_timeout=15`、`retries=3`、`extractor_retries=1`；`youtube-transcript-api` 1.x 没有显式 timeout，用线程池/`asyncio.wait_for` 包 **30s** 上限；失败返回可读中文错误，不要卡住整条流。
7. 平台选择：M1 若用 Cloudflare，**先灰云（DNS only）**；开启橙云前必须确认心跳已上线。

### 2.4 选型结论

- **首周灰度用 B（Railway）**：验证注册/登录、SSE 30 分钟、SQLite 卷持久性，成本低、回滚快。
- **稳定后迁 A（VPS + Caddy）**：超时、限流、备份、进程模型全部自己说了算；同域静态最稳。
- **C/D 只作为备选**：C 的磁盘会带来秒级停机；D 需要维护 `fly.toml`，适合已熟悉 Fly 的团队。
- **E 不进入上线路径**：登录态依赖第三方 Cookie，Safari 直接失败；即便 Chrome 能用，也把安全边界交给了两个平台的 CORS/Cookie 语义。
- **F 不在本期**：换 Postgres/Turso 需要重写 `sqlite3` 直连与文件存储，属于架构改造，不应与上线窗口叠加。

```bash
# 3) SSE 长连接（选 60–90 分钟的视频：流本身会跑 10–30 分钟；-N 禁止缓冲）
curl -sS -N --max-time 1800 -X POST https://ln.example.com/api/process-video-stream \
  -H 'Content-Type: application/json' -u ln:'<basic-auth 密码>' \
  -d '{"url":"https://www.youtube.com/watch?v=<视频ID>","model":"gemini-2.5-flash"}' \
  | tee /tmp/sse.log | grep -m1 '^event: meta'

# 4) 断流后续译：Ctrl-C 停掉上面的 curl，再重跑一次，应立刻收到 cached meta 并继续补批
# 5) 重启恢复：systemctl restart lingua-nova 后重复 1)，history 文件仍在
# 6) 回滚演练：切到上一个 release 再切回，服务都正常
```

**回滚**：`ln -sfn /srv/ln/releases/<上一个> /srv/ln/current && systemctl restart lingua-nova`；Caddyfile 每次改动先 `cp` 备份，回滚后 `caddy reload`。回滚窗口内不删旧 release。

**风险**：basic_auth 凭据在小组内共享（可接受，M2 撤）；P0‑1 未修时并发用户会互相阻塞（M1 限定单用户组）；YouTube 机房 IP 触发 429（见 R2）；免费/低价机 1 vCPU 编译前端会慢，可在本机构建后上传。

```bash
# 未登录必须 401
curl -sS -o /dev/null -w '%{http_code}\n' https://ln.example.com/api/history     # 期望 401

# 登录 + Cookie 属性

  -d '{"email":"a@example.com","password":"<密码>"}' https://ln.example.com/api/auth/login \
  | grep -i '^set-cookie'

# 两个账号隔离：A 的文件名，用 B 的 Cookie 读 → 期望 404

curl -sS -o /dev/null -w '%{http_code}\n' -b /tmp/b.cookies "https://ln.example.com/api/history/$A_FILE"

# 登录限流：连续 11 次错密码，第 11 次期望 429（当前阈值 10 次/60s）
for i in $(seq 1 11); do
  curl -sS -o /dev/null -w '%{http_code} ' -H 'Content-Type: application/json' \
    -d '{"email":"a@example.com","password":"wrong"}' https://ln.example.com/api/auth/login
done; echo

# 会话过期：staging 里用 SQL 把该会话 expires_at 改成过去，再请求 /api/auth/me → 401
#   sqlite3 /data/app.db "update sessions set expires_at = 1;"   # 仅 staging 演练

# 并发两条流（两个账号），观察互不阻塞（P0‑1 修完后才有意义）
# 磁盘水位：/data 用量 >85% 时新处理应 503，且监控告警
# 恢复演练：停服 → 用昨日备份恢复 app.db + users → 启动 → 老账号能登录、历史还在
```

**风险**：Cookie 名/域名/`Secure` 变更导致全员登出（发版前用 curl 对比）；迁移脚本不可逆；隔离改造漏改一处（逐点验收 `routes_videos`/`routes_user`/`translate`/`routes_content` 的 `storage.*` 调用）；无邮箱验证 → 垃圾注册（靠开关 + IP 限流 + 邀请码兜底）；单进程阻塞在多用户下暴露（M2 前必须修或临时 2–4 worker）。

### 5.3 `deploy/entrypoint.sh` 与容器内 Caddyfile（草案）

```sh
#!/bin/sh
set -eu
mkdir -p "${HISTORY_DIR:-/data/history}" "${SUBTITLES_DIR:-/data/subtitles}" "${USER_DATA_DIR:-/data/users}"
caddy start --config /etc/caddy/Caddyfile --adapter caddyfile
cd /app/backend
exec uvicorn main:app --host 127.0.0.1 --port 8000 \
  --workers 1 --proxy-headers --forwarded-allow-ips=127.0.0.1 --timeout-keep-alive 75
```

```caddyfile
:{$PORT:8080} {
    encode zstd gzip
    root * /app/frontend/dist
    handle /api/* {
        reverse_proxy 127.0.0.1:8000 {
            flush_interval -1
            transport http {
                read_timeout 24h
                response_header_timeout 24h
            }
        }
    }
    handle {
        try_files {path} /index.html
        file_server
    }
}
```

**草案的已知坑（上线前逐条处理）**：

1. **PID 1 与信号**：`caddy start` 会 daemon 化，`exec uvicorn` 让 uvicorn 成为 PID 1；平台停容器时 Caddy 由运行时回收。能跑，但不优雅；正规做法是 Caddy 放宿主机（M2 的 VPS 方案）。
2. **卷权限**：容器以 UID 1000 运行，Volume 挂载后 `/data` 属主可能是 root → 启动即 `PermissionError`。平台侧初始化卷后执行 `chown -R 1000:1000 /data`，或首次启动用 root 建目录再降权。
3. **`VITE_API_BASE` 是构建参数**：构建产物里的 API 地址在 `docker build` 时固定；改域名必须重新构建，不能只改运行时环境变量。
4. **`HISTORY_DIR` 在 import 时创建**：卷没挂好会直接启动失败（这是好事，暴露配置问题），但平台会显示成「服务不断重启」，要会看日志。
5. **`/health` 不查 DB**：平台探活会显示健康，即使 `app.db` 损坏；M2 必须加 `/healthz`。
6. **Caddy 二进制来源**：草案从 `caddy:2-alpine`（musl 静态构建）复制，在 Debian 上通常可用；若运行时报动态链接错误，改用 `caddy:2`（Debian 基础镜像）复制或按官方源安装。

```bash
rclone copy "$OUT" "r2:ln-backup/$(date -u +%Y/%m)" --include "*-$STAMP.*" --checksum
find "$OUT" -type f -mtime +14 -delete
```

### 6.5 故障处置速查

| 现象 | 先查 | 处置 |
|---|---|---|
| 全站 502 | `systemctl status`、`journalctl -u` | 进程崩了 → 看堆栈；端口不对 → 检查 `--port` 与 Caddy `reverse_proxy` |
| SSE 60s 就断 | 是否有心跳；反代是否缓冲 | 加心跳；Caddy `flush_interval -1` / Nginx `proxy_buffering off` + 长超时 |
| 一个用户开流后全站卡 | P0‑1 是否修 | 临时 `--workers 2`；根治：阻塞调用移入 `to_thread` |
| 登录后立刻 401 | Cookie 是否 `Secure` + HTTPS；CORS 是否精确；`SameSite` | 用 `curl -D -` 对比 `Set-Cookie`；同域部署；检查时钟 |
| `database is locked` | 是否多 worker/多进程；是否长事务 | 保持单写进程；`busy_timeout`；迁移在停服时做 |
| 磁盘满 | `df -h /data`、`du -sh /data/users/*` | 清理 90 天前缓存；临时扩卷；开 C17 的 503 闸门 |
| YouTube 429 | 日志里的 `IpBlocked/RequestBlocked` | 降频、换出口、加缓存；提示用户稍后再试（不要无限重试） |
| 备份缺失 | 对象存储与 cron 日志 | 立即手工跑一次 `backup.sh`；检查 rclone 凭据与存储配额 |
| 证书到期 | `caddy` 日志 / 平台面板 | 自动续期失败多为 80 端口被挡；放行 ACME 或改 DNS-01 |

## 7. 风险登记

| ID | 风险 | 概率/影响 | 触发信号 | 缓解 | 应急预案 |
|---|---|---|---|---|---|
| **R1** | 公网暴露 API Key（`VITE_API_KEY`、`.env` 进镜像、日志回显） | 中 / 极高 | `frontend/dist` 里搜到 key；账单异常 | C05 不设共享 key；`.dockerignore`；只用手服务端 env；密钥按环境分开并设预算 | 立即轮换 Gemini/DeepSeek key；下线旧构建；查账单/日志确认滥用范围 |
| **R2** | 抓取 YouTube 的反爬与合规 | 高 / 高 | 日志 429 激增、`RequestBlocked`；收到投诉 | 仅个人学习用途的封闭 beta；限流+缓存；不对外分发字幕；不提供下载；保留删除能力；考虑出口代理 | 关闭新处理（`REGISTRATION_OPEN=0`/维护页）；清理争议内容；必要时暂停字幕抓取，改为用户上传 SRT |
| **R3** | 大模型配额被滥用 | 高 / 高 | 单用户调用量/费用异常；429 激增 | 登录后才可用；每用户日预算；全局并发 4；登录/注册限流；模型目录只留已定价模型 | 关注册 + 封禁账号 + 临时降级到便宜模型 + 设全局日预算硬闸 |
| **R4** | SSE 超时/断流 | 高 / 中 | 客户端「处理失败」；日志里流被中断 | 15s 心跳；反代超时 3600s；单流 45 分钟上限；断流自动重开续译 | 让用户刷新（缓存回放+补译）；必要时临时缩短单视频上限 |
| **R5** | SQLite 单点 | 中 / 高 | `database is locked`、`integrity_check` 失败、磁盘满 | 单写进程 + WAL + busy_timeout；磁盘水位闸门；每日备份；每周 integrity_check | 停服 → 用最近备份恢复 → 回放日志补差异；持续故障再评估 Postgres |
| **R6** | 备份丢失/不可恢复 | 中 / 极高 | 备份任务静默失败；恢复演练报错 | 3-2-1：本地 + 对象存储；校验和；备份缺失告警；每月恢复演练 | 从对象存储历史版本找回；仍失败则如实告知用户数据丢失范围（不要假装恢复成功） |
| R7 | 跨用户数据泄漏 | 低 / 极高 | 越权测试失败；异常路径日志 | 每用户目录 + realpath 校验 + 越权测试纳入发布门禁 | 立即停服、封禁入口、评估影响面、通知受影响用户、修完再上线 |
| R8 | 账号滥用（无邮箱验证） | 高 / 中 | 注册量突增、同 IP 多账号 | 注册开关 + IP 限流 + 邀请码；M3 加邮箱验证 | 关注册、清垃圾账号、加验证码/邀请制 |
| R9 | 磁盘写满导致全站 500 | 中 / 高 | 磁盘 >85%、写错误日志 | 配额 + 90 天清理 + 水位 503 + 告警 | 扩卷/清缓存；先恢复写能力再查根因 |
| R10 | 中国大陆网络与备案 | 高 / 中 | 用户打不开或极慢；YouTube 不可达 | 机房放海外（新/日/美/欧）；明确目标用户需能访问 YouTube；境内落地需 ICP 备案且 YouTube 本身不可达 → **不建议境内机房** | 换海外节点/加 CDN；如实说明网络前提，不承诺境内可用性 |
