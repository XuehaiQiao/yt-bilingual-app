## 0. 一页结论

1. v1.1 的 schema 变更只有 `0033_v1_1_launch`：**新增 2 张表 + 1 个可空列**，不改旧行、不删列、不改 ID。
2. 整条链路已在隔离副本上演练通过：**升级 0032→0033 → 校验 → 降级回 0032 → 校验 → 再升级（幂等）→ 整库恢复 → 校验**，旧表逐表内容哈希一致、`integrity_check=ok`、`foreign_key_check` 无违规、`data/users` 92 文件哈希不变；真实 `data/` 未被触碰（SHA256/mtime 前后一致）。
3. 迁移本身很轻：本机实测 **upgrade 264 ms / downgrade 297 ms**；整个演练 9 s（大头是备份 3.4 s + 恢复 2.0 s）。停写窗口按 **5–10 分钟** 准备足够。
4. 回滚有三层：代码回滚（首选，旧代码兼容 0033 库）→ `alembic downgrade 0032_pipeline_timing`（会丢 v1.1 新数据）→ 整库恢复备份（最后手段）。
5. 用户感知最小化成立：不换 ID、不动进度/词书/缓存、不强制重新登录（`sessions` 哈希不变）、不强制邮箱验证（旧用户 `email_verified_at` 保持 NULL）、旧 URL 不变。
6. 上线前必须补齐的运维条件：**SMTP 已配置**（否则找回密码邮件只进 dev outbox，接口却恒返回 200）、离机备份已配、`scripts/v11_backup_status.sh` 与告警已经接上。

## 1. v1.1 变更面（决定"要备份/要校验什么"）

### 1.1 数据库（唯一迁移：`0033_v1_1_launch`，`down_revision=0032_pipeline_timing`）

| 对象 | 变更 | 回滚 |
|---|---|---|
| `auth_tokens`（新表） | `id, user_id, purpose, token_hash(UNIQUE), expires_at_ms, used_at_ms, created_at_ms, email`；4 个索引 | downgrade 删表 |
| `feedback`（新表） | `id, user_id(可空), request_id(可空), category, message, contact, status='open', created_at_ms, resolved_at_ms, admin_note`；2 个索引 | downgrade 删表 |
| `users.email_verified_at` | 新增可空列；旧行保持 NULL = 未验证 | downgrade 用 batch 重建 `users` 表删列 |

迁移特性（与 `0033` 文件头一致）：只加不删、`upgrade`/`downgrade` 都先查再建/再删（可重复执行）；`token_hash` 只存 hash、不存明文；`feedback` 故意不建外键（账号硬删不级联）。

### 1.2 应用面（上线检查项，不属于迁移风险）

- 账号找回：`POST /api/auth/password-reset/request`（**恒 200**，不枚举邮箱）、`/confirm`。
- 邮箱验证：`POST /api/auth/email-verification/request`（登录态，202）、`/confirm`。
- 登录/`me` 响应**追加** `emailVerified`（旧字段不变；false 不阻断登录/使用）。
- 反馈（P2-39 交付）：`POST /api/feedback`（登录/游客均可）、管理台 `GET/PATCH /api/admin/feedback`。
- 用户额度（P2-39 交付）：`GET /api/quota`（登录，只读）。
- 邮件：SMTP 可插拔（`SMTP_*` / `PUBLIC_BASE_URL`）；**未配置时写 dev outbox，不真实发信**。
- 前端新增入口（反馈/额度/首次激活/AI 标识）：只增不改；**发布前确认旧入口/旧路由未变**。

### 1.3 明确的"用户感知最小化"承诺（逐条可验）

| 承诺 | 验收方式 |
|---|---|
| 用户 ID 不变 | `users.id` 逐表哈希一致；8 行快照不变 |
| 进度/词书/复习状态不变 | `user_wordlist_items`(7511)、`word_states`(17)、`review_logs`(12)、`weekly_reports`(1801) 行数与哈希一致 |
| 用户文件/缓存不变 | `data/users/` 92 文件、聚合 SHA256 一致 |
| 不强制重新登录 | `sessions`(121) 哈希不变；迁移后直接用旧 Cookie 访问 `/api/auth/me` |
| 不强制邮箱验证 | `users.email_verified_at` 全 NULL；登录/翻译不因 `emailVerified=false` 被拦 |
| 不强制改密 | `users.password_hash` 不变（含在 users 哈希里） |
| 旧 URL 不变 | 旧书签逐条打开：`/`、`/watch…`、`/reading`、`/wordbook`、`/#/account`、`/#/privacy`、`/#/terms` |
| 迁移期间不新增 AI 花费 | 迁移动作不触发翻译/分析 |

## 2. 备份（上线前置条件）

### 2.1 备份什么、不备份什么

`scripts/backup.sh` 的边界（脚本头契约，未改动）：

| 内容 | 是否在备份 | 说明 |
|---|---|---|
| `data/app.db` | ✅ `sqlite3 .backup`（WAL 安全，可在线执行） | 备份内做 `PRAGMA integrity_check` |
| `data/users/<id>/`（历史/导入书/缓存） | ✅ 整目录复制 + 每文件 SHA256 + 聚合哈希 | 92 文件 / 3.5 MB（当前工作区） |
| `.env` | ⚠️ 只存**键名**（`config/env.keys`） | 值/密钥永不入备份 |
| `data/guests/`（游客按 hash 目录） | ❌ | 当前 1663 文件 / 6.7 MB；游客进度属可丢数据，若要保游客连续性需另加一步（见 §2.4） |
| `data/ecdict.db`（112 MB 词典） | ❌ | 可用 `scripts/fetch_dictionary.py` 重建 |
| `data/curated-subtitles/`、`data/reports/`、`data/backups/`、`history/`、`subtitles/` | ❌ | 可重建/运行时产物/版权内容（`history/` 为旧版遗留） |

### 2.2 三个时机

1. **每日**：`deploy/backup.cron`（03:17，`--keep 7`）→ `$BACKUP_ROOT`。
2. **上线前（必须）**：停写后再跑一次，归档复制到 `$BACKUP_ROOT/pinned/`（子目录不参与 `backup.sh` 的 `-maxdepth 1` 清理，不会被 `--keep` 顺手删掉）。
3. **离机**：`rclone copy` 到 R2/B2（`deploy/backup.cron` 示例；先加密，见 §2.4）。

### 2.3 命令（`$DATA` 为数据根目录，见 §3.1 路径映射）

```bash
# 每日/上线前备份（生产用 ln 用户执行；Docker 用 docker compose exec 进容器执行同一脚本）
cd /srv/ln/current
DATA_DIR=/srv/ln/data AUTH_DB_PATH=/srv/ln/data/app.db USER_DATA_DIR=/srv/ln/data/users \
BACKUP_ROOT=/srv/ln/backups ENV_FILE=/etc/linguatrek/env \
  scripts/backup.sh --keep 14

# 归档固定保留（上线/回滚窗口内不许删）
mkdir -p /srv/ln/backups/pinned
cp -p /srv/ln/backups/linguatrek-backup-*.tar.gz /srv/ln/backups/pinned/

# 验收：包龄/可读/表数/用户数/manifest
scripts/v11_backup_status.sh --backup-root /srv/ln/backups --max-age-hours 26
tar -xzOf /srv/ln/backups/pinned/<stamp>.tar.gz '*/manifest.env' | grep -E 'DB_SIZE|DB_SHA256|TABLE_COUNT|USER_COUNT|USER_FILE_COUNT|USERS_TREE|ALEMBIC'

# 离机（加密后上传；私钥/口令进密码管理器，不进仓库）
age -r <公钥> -o /srv/ln/backups/pinned/<stamp>.tar.gz.age /srv/ln/backups/pinned/<stamp>.tar.gz
rclone copy /srv/ln/backups/pinned r2:linguatrek-backup/pinned --include '*.age' --checksum
rclone check /srv/ln/backups r2:linguatrek-backup/daily --include 'linguatrek-backup-*.tar.gz'
```

保留策略（建议）：

| 层 | 位置 | 保留 | 用途 |
|---|---|---|---|
| 日备 | `/srv/ln/backups` | 7–14 份（`--keep`） | 日常误删/回滚 |
| 上线/里程碑固定包 | `/srv/ln/backups/pinned` + 离机 `pinned/` | **≥ 30 天**（v1.1 回滚窗口） | 本次迁移回滚 |
| 离机日备 | `r2:.../daily` | 30 天（生命周期规则） | 整机故障 |
| 月度冷备 | `r2:.../monthly` | 90 天 | 合规/长期 |

### 2.4 游客目录（当前不在备份内）

- 现状：`data/guests/<sha256(guest cookie)>/*`，1663 文件 / 6.7 MB；游客进度、看过的视频缓存。

### 3.2 T-3：冻结与演练

1. **冻结发布物**：`git rev-parse --short=7 HEAD` → 记 release sha；确认 `git status --porcelain` 里只剩本卡允诺的改动；确认 `0033_v1_1_launch` 已合入。
2. **确认迁移图**：`venv/bin/python -m alembic heads` 应只输出一个 head（当前 `0033_v1_1_launch`）；`cd backend && venv/bin/python -m alembic history | head -3` 核对链条。
3. **配 SMTP / `PUBLIC_BASE_URL`**（没有就先别公开"找回密码"入口）：`SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASSWORD`、`SMTP_FROM`（或 `SMTP_SSL=1`）、`PUBLIC_BASE_URL=https://linguatrekai.online`。验证：一个测试账号走一次找回，收到邮件且 token 只在邮件里（日志/DB 无明文）。
4. **在隔离副本上演练**（不碰生产）：
   ```bash
   # 取生产/预发的数据副本（只读），在临时区跑完整演练
   scripts/rehearse_v11_migration.sh --source-data /tmp/prod-copy/data --keep
   ```
   要求：`结论 PASS（全部步骤通过）`；同时把 `--from-rev` 设为**生产实际 current**（若生产低于 0032，会一次跨多个迁移，见 §3.6）。
5. **记录迁移前基线**（生产，停写后）：
   ```bash
   python3 scripts/v11_data_snapshot.py --db $DATA/app.db --users $DATA/users \
     --out /tmp/v1.1-pre-<stamp>.json
   ```
   期望输出：`表数 / 行数 / alembic_version / integrity=ok / FK 违规=0` 与运维记录一致。

### 3.5 迁移前后校验（全部必过才放量）

```bash
# A. 版本与就绪
cd /srv/ln/current/backend && AUTH_DB_PATH=$DATA/app.db venv/bin/python -m alembic current   # 必须 = head
curl -fsS http://127.0.0.1:8000/healthz | python3 -m json.tool
#    status=ok；db.ok=true；db.migrations.current == db.migrations.head == 0033_v1_1_launch

# B. 新旧库对照（表/行数/关键表内容哈希/用户目录哈希/integrity/FK）
python3 scripts/v11_data_snapshot.py --db $DATA/app.db --users $DATA/users \
  --compare /tmp/v1.1-pre.json
#    PASS：没有表消失；预期新增 auth_tokens / feedback；共同表行数与内容哈希一致；
#          users 新增 email_verified_at；users 目录文件数与聚合 SHA256 一致

# C. 直接 SQL 抽查（与业务读数对得上）
sqlite3 -readonly $DATA/app.db "select count(*) from users;"                      # 与基线一致
sqlite3 -readonly $DATA/app.db "select count(*) from users where email_verified_at is not null;"  # 0
sqlite3 -readonly $DATA/app.db "select count(*) from auth_tokens; select count(*) from feedback;" # 0 / 0
sqlite3 -readonly $DATA/app.db "pragma integrity_check; pragma foreign_key_check;" # ok / 空

# D. 启动服务 + 冒烟（见 §3.8）
```

通过标准（缺一不可）：`integrity_check=ok`、`foreign_key_check` 空、无表消失、旧表哈希全一致、`data/users` 哈希一致、`alembic current=head`、`/healthz` 200。

### 3.6 跨多版本迁移（生产 current < 0032 时）

- `alembic upgrade head` 会按序执行缺的迁移：`0026_seed_band_fix`（**会清空 `user_skill_profiles` 里旧种子行的 `cefr_low/cefr_high`**，有意修正；该迁移 downgrade 是空操作，升级后不可反向恢复旧值）、`0027`（`word_states.mastered`）、`0028/0029`（词表/释义列）、`0030`（写 `model_prices`）、`0031`（`quota_overrides`）、`0032`（`pipeline_timing`）、`0033`。
- 演练时用 `--from-rev <生产 current>` 跑一遍；校验脚本会指出 0026 带来的 `user_skill_profiles` 行内容变化（属预期，记录在案即可）。

## 4. 回滚

### 4.1 决策树

```
现象：上线后能否用？
├─ 业务可用，只是新功能有 bug（找回/反馈/额度/验证）
│   → 层级 1：代码回滚到上一个 release（DB 保留 0033，旧代码不读新表）  ← 默认
├─ 新代码因 0033 表/列报错（如 sqlite 写入冲突、schema 相关 500），且代码回滚不能解决
│   → 层级 2：alembic downgrade 0032_pipeline_timing（删 2 表 + 重建 users 删列）
│       代价：auth_tokens/feedback 新数据丢失；已有 emailVerified 状态丢失（旧行仍 NULL 可登录）
└─ 数据本身坏了（integrity/FK 异常、写入错乱）或层级 2 失败
    → 层级 3：停服 → restore.sh 恢复 pinned 备份（丢迁移后的全部写入）
```

时限：**T+24 h 内**优先层级 1；层级 2 在 T+72 h 内可用（之后新数据变多，代价上升）；层级 3 任何时候都可执行，但需回滚决策人签字。

### 4.2 命令

```bash
# 层级 1：代码回滚（保留 0033）
# 裸机：切 release + 重启
ssh ln@<host> "ln -sfn /srv/ln/releases/<上一个> /srv/ln/current && sudo systemctl restart lingua-nova"
# Docker：切回上一个镜像 tag 并重启
cd /srv/ln/app && docker compose up -d --force-recreate app
curl -fsS http://127.0.0.1:8000/healthz        # 旧代码遇到 0033 库：ok；current 仍=0033

# 层级 2：schema 回滚（会删 v1.1 新数据；先备份当前库！）
sudo systemctl stop lingua-nova
cd /srv/ln/current
DATA_DIR=$DATA AUTH_DB_PATH=$DATA/app.db BACKUP_ROOT=/srv/ln/backups scripts/backup.sh --keep 14
cd backend && AUTH_DB_PATH=$DATA/app.db venv/bin/python -m alembic downgrade 0032_pipeline_timing
AUTH_DB_PATH=$DATA/app.db venv/bin/python -m alembic current          # = 0032_pipeline_timing
python3 /srv/ln/current/scripts/v11_data_snapshot.py --db $DATA/app.db --users $DATA/users \
  --compare /tmp/v1.1-pre.json --allow-new ""                          # 必须 PASS
sudo systemctl start lingua-nova

# 层级 3：整库恢复（最末手段）
sudo systemctl stop lingua-nova
/srv/ln/current/scripts/restore.sh /srv/ln/backups/pinned/<stamp>.tar.gz \
  --to $DATA --force          # 旧数据自动移到 $DATA/.pre-restore-<stamp>
sudo systemctl start lingua-nova
curl -fsS http://127.0.0.1:8000/healthz
```

注意：层级 2 的 downgrade 会 `batch_alter_table` **重建 `users` 表**（SQLite 删列必经路径）。本次演练已验证数据逐表哈希不变，但要求磁盘余量 ≥ 2× `users` 表大小，且必须停写；不要在有长事务时执行。

### 4.3 回滚后校验（与升级同一套）

- `alembic current` = 回滚目标；`/healthz` 200。
- `v11_data_snapshot.py --compare /tmp/v1.1-pre.json --allow-new ""` → PASS（层级 2/3 必须逐表一致；层级 1 允许 0033 新表存在）。
- 老账号可登录、词书/进度读数不变；旧 URL 可打开。
- 记录：回滚层级、时间、操作人、丢失数据范围（层级 2：v1.1 新写入；层级 3：备份点之后全部写入）。

## 5. 失败处理

| 症状 | 先查 | 处置 |
|---|---|---|
| `alembic upgrade` 报 `database is locked` | 是否有第二个进程/多 worker 在写；是否有长事务 | 停服再跑；保持单写进程；`PRAGMA busy_timeout` 已由应用设置 |
| `alembic upgrade` 报 `duplicate column`/`table already exists` | 是否手工建过/重复跑 | 0033 幂等，重跑即可；仍失败则 `alembic current` 对比 `alembic history`，用 `--sql` 离线看语句 |
| 升级成功但 `/healthz` `status=degraded`（`db.ok=false`） | 磁盘/权限/DB 可读性 | 看 `journalctl`；`sqlite3 -readonly ... 'pragma integrity_check'`；必要时层级 3 |
| `db.migrations.current != head` | 迁移没跑/跑到一半 | 重跑 `upgrade head`；确认 `AUTH_DB_PATH` 指向正确库（Docker 路径映射） |
| 登录后立刻 401 / 掉线 | `COOKIE_SECURE`、`CORS_ORIGINS`、时钟、代理 | 同域部署；`curl -D -` 比 `Set-Cookie`；**不要**借此清 sessions |
| 找回密码接口 200 但用户收不到信 | `SMTP_HOST`/`SMTP_FROM`/`PUBLIC_BASE_URL`；dev outbox 是否有文件 | 补齐 SMTP 配置并重启；客服先用人工重置兜底 |
| 反馈提交 500/503 | `feedback` 表是否存在（0033 是否真跑）、限流 | `alembic current`；看 `journalctl` 栈；临时用邮件兜底收反馈 |
| 429 激增 | 限流桶（登录 10/60s/IP 等）、是否有脚本刷 | 网关加白名单/封 IP；确认不是前端重试风暴 |
| 402 激增 | 余额/价格配置（`model_prices`、`MODEL_CATALOG`）、`BILLING_STRICT` | 核对价格；必要时临时调高预算/充值；属资金口径问题要拉财务/管理员 |
| 磁盘水位告警 | `df -h $DATA`、`du -sh $DATA/users/*` | 清理 90 天前缓存；**当前无自动水位闸**（C17 未实现），靠维护模式/停新处理止血，再扩容 |
| SSE 断流/首字慢 | 反代缓冲/超时、心跳、模型 429 | 见 `docs/计划-上线部署.md` §6.5；回滚模型路由 |
| 迁移后某些页面慢 | 新索引缺失（手工建过表时 0033 会补索引）、`pipeline_timing` 查询量 | `EXPLAIN QUERY PLAN`；确认 4 个 `auth_tokens` 索引 + 2 个 `feedback` 索引存在 |

失败时的通用原则：**先止血（维护模式/回滚代码），再定位**；任何"重跑迁移"之前先备份当前库到 `pinned-rollback/`。

## 6. 告警阈值建议

采集点：`/healthz`（进程外每 2 分钟，已有 `scripts/check-alerts.py` + `deploy/alert-check.cron`）、访问日志（`v11_launch_metrics.py`）、`GET /api/admin/pipeline-timing`、`scripts/v11_backup_status.sh`、`df`、内置告警（5xx/LLM 失败率/预算阈值）。

> 下列为**起始阈值**，上线后按 7 天基线校准（相对阈值 = 滚动基线 ±50% 触发，绝对阈值兜底）。

| 指标 | 采集 | 警告（P1） | 严重（P0） | 动作 |
|---|---|---|---|---|
| API P95 延迟 | 访问日志（排除 /health、/healthz） | > 1500 ms 持续 5 min | > 2500 ms 持续 10 min | 查慢路径（脚本给出 P95 Top5）；回滚代码/降级模型 |
| HTTP 5xx 率 | 访问日志 | > 1%（10 min，≥50 请求） | > 5% 或 `/healthz` 连续 2 次失败 | 止血：维护模式/回滚；看 request_id 栈 |
| 429 率 | 访问日志 | > 2%（15 min） | > 10%（15 min） | 查限流桶/刷量；公告"稍后再试"；必要时放宽单用户额度 |
| 402 率 | 访问日志 | > 1%（15 min） | > 5%（15 min） | 查价格/余额/预算配置；余额问题客服兜底 |
| 备份新鲜度 | `v11_backup_status.sh`（cron 每日 1 次） | 最新包 > 26 h 或归档数 < 3 | > 48 h 或 tar 不可读 | 立即手工备份；查 cron/rclone/磁盘 |
| 恢复演练 | `restore_drill.sh`（月度） | 任一次 FAIL | — | 演练失败 = 备份不可信，当日修复 |
| 磁盘 | `df` + `GET /api/admin/health`（返回 `disk` 占用） | 剩余 < 15% | 剩余 < 10% | 清理缓存/扩容；必要时维护模式止血（**当前没有自动水位闸**，见 §10） |
| 迁移漂移 | `/healthz` `db.migrations.current` | 发布后 10 min 仍 ≠ head | 持续 1 h | 重跑迁移或回滚 |
| LLM 失败率 | 内置（10 min 窗口 ≥20% 且 ≥10 次） | 已有 P1 | 连续 30 min | 切模型路由/降额度 |
| 日预算 | 内置（50/80/100%） | 50/80% P1 | 100% | 限流/公告/调额度 |
| 翻译管 P95/成功率 | `/api/admin/pipeline-timing` | P95 比 7 天基线 +50% 或成功率 <95% | 成功率 <85% | 查模型/网络；必要时回滚 |
| SSE 断流 | 用户反馈 + timing 失败率 | 每小时 ≥ 3 例 | 集中爆发/首字 > 60 s | 查反代/心跳/模型 |

配套：`scripts/check-alerts.py --event backup_failed --level P1 --summary "..."` 复用已有飞书通道；维护模式会静默 P1/P2（P0 仍发），计划内窗口先打维护模式减少噪音。

| 生产实际 current 可能 < 0032 | 一次跨多迁移，0026 会清空 `user_skill_profiles` 旧种子区间且不可逆 | 上线前 `alembic current` 记录；用 `--from-rev <current>` 演练；停写窗口放宽 |
| `0033` downgrade 重建 `users` 表 | 需磁盘余量、停写；表大时耗时增加 | 已在副本验证；执行前先备份当前库；不在长事务期做 |
| SMTP 未配置 | 找回密码"成功"但用户收不到信 | 上线前配置并实测；客服人工重置兜底 |
| 反馈无独立 kill switch | 出问题时只能发版隐藏入口 | 后端限流 + 尽快补 flag；先接受 |
| `data/guests` 不在备份 | 游客进度丢失 | 明文写入客服话术；或按 §2.4 追加 tar |
| 离机备份可能仍未配置（历史缺口） | 整机故障=数据全丢 | 上线前置条件：`rclone check` 通过才发 |
| C17 磁盘水位闸、`/api/flags` 远端开关未实现 | 磁盘满时无自动 503 闸；功能开关只能发版 | 监控 + 维护模式止血；后续补实现（不在本卡范围） |
| 迁移期间维护模式会静默 P1/P2 | 计划内告警噪音降低，但可能漏 P1 | P0 仍发；窗口后立刻取消维护模式并补看日志 |
| 演练在本机、非生产 | 卷权限/磁盘/负载差异 | 上线前在预发/生产副本上再跑一次（`--source-data`） |
