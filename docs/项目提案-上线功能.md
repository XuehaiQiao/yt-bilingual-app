## 1. 一页结论

### 1.1 一句话结论

**首发只做 G1 邀请制免费内测：海外服务器 + Caddy Basic Auth 外层挡人 + 站内邀请码注册；G2 的注册开关、账号删除/导出、余额与成本计量、飞书告警等能力同期建好但默认关闭；不收费、不接邮件、不做支付；等全部功能完成并验收后，再单独出详细上线步骤。**

### 1.2 目标、形态与边界

| 项目 | 结论 |
|---|---|
| **首发形态** | G1 邀请制免费内测；Web only；10–30 名已知用户；不开放公开注册 |
| **访问控制** | A 层：网关 Basic Auth（Caddy，挡在整站前）；B 层：应用内邀请码（注册时校验）。两层独立，缺一不可 |
| **服务器** | 海外 VPS（新加坡/东京/美西/欧洲待定）；功能先行；域名同步购买，部署后置 |
| **收费** | 不收费；无支付/订阅/退款/发票；余额不是商品，不可购买、不可提现 |
| **新用户余额** | 默认 **$2.00 = 2,000,000 µUSD（micro-USD）**；用完后管理员后台手动充值 |
| **AI 成本** | 尽量按“真实 token 用量 × 可靠单价”记录每次调用；无法做到绝对准确，边界见 §5.9 |
| **告警** | 飞书自定义机器人 webhook；不把 webhook/签名密钥写入仓库 |
| **运营主体** | 个人运营；发布负责人、值班、客服、成本、法务均由用户本人承担 |
| **G2 状态** | 能力建设、默认关闭。**无邮箱验证/通知时，不满足真正公开自助注册的条件**；详见 §4.5 与 §11.3 D-8 |
| **本轮交付** | 仅本文档；代码/迁移/测试/部署/详细上线步骤均为后续交付物 |

### 1.3 为什么先做 G1

1. **账号生命周期还不完整**：当前只有 `signup/login/logout/me/claim-guest`，没有邮箱验证、找回密码、改密、删号；`auth_db.delete_user_sessions()` 已定义但仓库内无调用方。公开注册会把“忘记密码 = 丢账号”直接暴露给陌生人。
2. **法务页还没上线**：页脚隐私政策/使用协议仍是 `ComingSoon`，账户页仍显示 `legalPending`。G1 可以用邀请制 + 公告 + 人工客服兜底，G2 不行。（2026-11-20 M4 已补：`#/privacy`、`#/terms`、注册披露与本地视频文案已落地；仍无真实可收信联系渠道、未做法务复核。）
3. **成本还没对账**：`MODEL_CATALOG` 里除 `gemini-2.5-flash` 外，DeepSeek/Gemini 3.x/Qwen 的价格均为 `None`；账本缺价时按“已知最贵”计，是上限估算，不是厂商账单。没有可靠单价就公开注册，等于把成本风险交给未知用户。
4. **个人运营的响应能力有限**：单人值班、单 SQLite 写进程、单 uvicorn worker；G1 的 10–30 人规模可以人工兜底，G2 的滥用/客服/合规压力不匹配。
5. **先验证学习闭环**：G1 的目标不是增长，而是验证“注册 → 学习 → 反馈 → 留存”是否成立，并收集真实成本数据，为 G2 的开放条件提供依据。

### 1.4 G2 能力“先建但不开放”的含义

- **建什么**：`REGISTRATION_OPEN` 开关、邀请码体系、删除/导出、余额/成本、限流、审计、飞书告警、法务页与文案、公开站基础项。
- **不建什么**：邮箱验证、邮件通知、找回密码邮件、支付/订阅、未成年人流程、移动端/PWA、SEO 大改、ASR 承诺。
- **默认值**：`REGISTRATION_OPEN=false`；没有有效邀请码不能注册；公开注册路径只存在于代码与测试中，不对真实用户暴露。
- **开放条件**：G2 真正开放前，必须另行评审。没有邮箱验证时，至少要有“持续邀请码 + 人工找回/删除/导出 + 监控告警”的替代方案；否则不应把 `REGISTRATION_OPEN` 改为 `true`。

### 1.5 用户已拍板的决策（原样纳入）

| # | 决策 | 在本提案中的落点 |
|---|---|---|

| 2 | 邀请方式 A+B：A=网关 Basic Auth；B=站内邀请码 | §3、§7 |

| 5 | 删掉错误文案“字幕只在本地读取，不会上传”；其他隐私合规项暂不扩展 | §8 |

### 1.6 G1 的成功标准（建议）

- 10–30 名邀请用户中，至少 80% 完成一次“打开内容 → 翻译/学习 → 收藏或复习”的闭环。
- 无 P0 数据丢失、无越权、无网关绕过；删除/导出请求在 7 个工作日内可执行。
- 每次 AI 调用都有账本记录；已知价模型的月度账本与厂商账单差异可解释（目标 ≤2%，不含折扣/缓存/失败调用的不可见计费）。
- 飞书 P0 告警可送达；备份与恢复演练有证据；无“不知道是否正常”的时段。
- 余额不足、配额用尽、网关 401、邀请码失效都有可读文案，不出现“服务器错误”。

## 3. 用户旅程

### 3.1 G1 新用户：网关 → 邀请码 → 注册 → 登录 → 学习

| 步骤 | 参与者 | 系统行为 | 失败/异常 |
|---|---|---|---|
| 1 | 管理员 | 在后台生成邀请码；把“网关账号 + 邀请码”通过站外渠道（IM/私信）发给用户 | 邀请码只显示一次；丢失只能重新生成 |
| 2 | 用户 | 打开 `https://<domain>/`；浏览器弹出 Basic Auth，输入网关账号 | 无凭据/错误 → Caddy 401；不进入应用 |
| 3 | 用户 | 页面加载；前端读取 `GET /api/auth/registration`，显示“邀请制内测，需要邀请码” | 网关通过但应用关闭注册 → 注册按钮禁用/说明 |
| 4 | 用户 | 填写邮箱、密码、用户名、邀请码，提交 `POST /api/auth/signup` | 邀请码无效/过期/撤销/用完 → 403 统一文案；邮箱已注册 → 409；限流 → 429 |
| 5 | 服务端 | 校验邀请码（原子占用）→ 创建用户 → 写入 $2.00 开户奖励与流水 → 创建会话 → `Set-Cookie: ln_session` | 任一写库失败回滚整个开户；不产生“有用户没余额/没邀请记录”的半成品 |
| 6 | 用户 | 进入应用；开始看视频/本地视频/复习 | AI 调用受日配额、日预算、余额约束；不足时 429/402 可读文案 |
| 7 | 用户 | 下次访问：网关 Basic Auth + 邮箱密码登录；**不需要再次输入邀请码** | 忘记密码：本轮无自助找回；按 §4.5 人工处理 |

### 3.2 G1 已有用户（已注册）

- 访问路径仍是“网关 Basic Auth → 应用登录”。邀请码只在注册时使用；撤销邀请码不会踢掉已注册用户。
- 要真正撤销某人的访问，必须同时做三件事：移除其网关账号（Caddy reload）、撤销其未用邀请码、在应用内封禁账号（`status='banned'`）或删除全部会话。只做其中一件都不够。
- 封禁后旧会话在下一次 `/api/*` 请求被中间件 403；但网关层仍会先放行，所以网关账号必须同步移除。

### 3.3 管理员：生成 / 撤销邀请码

1. 管理员以 `ADMIN_EMAILS` 中的邮箱登录；`/api/admin/*` 仍由应用层管理员校验，Basic Auth 不是管理员身份。
2. 打开“邀请码”页：选择数量（1–20）、有效期（1–90 天）、每码可用次数（1–10，G1 默认 1）、备注。
3. 生成后**只显示一次明文**；管理员复制并通过站外渠道发给用户。服务端只存哈希与前缀，之后无法再取回明文。
4. 列表显示：前缀、创建时间、过期时间、已用/上限、状态（可用/已用完/已过期/已撤销）、备注。
5. 撤销：立即生效；已用该码注册的账号不受影响，需要另行封禁。
6. 查看兑换记录：邮箱、用户 id、兑换时间；用于内测名单核对。邮箱是个人数据，仅管理员可见。

### 3.4 `REGISTRATION_OPEN=false` 的行为矩阵

| `REGISTRATION_OPEN` | 邀请码 | 注册结果 | 已有用户登录 | 说明 |
|---|---|---|---|---|
| `false`（默认） | 有效 | 允许 | 允许 | G1 正常态 |
| `false` | 缺失 | 403 `invite_required` | 允许 | 前端隐藏/禁用注册入口并说明“邀请制” |
| `false` | 无效/过期/撤销/用完 | 403 统一“邀请码无效或不可用” | 允许 | 不泄露具体原因；服务端审计真实原因 |
| `true` | 任意/缺失 | 允许（若提供无效码则拒绝） | 允许 | G2 能力；**默认不开启** |
| `true` 且 `INVITE_SIGNUP_ENABLED=false` | 任意 | 允许 | 允许 | 仅作为未来“完全开放”模式；G1 不使用 |
| 任一 | 管理员/测试 | 仍走正常注册；不提供“管理员免邀请”后门 | 允许 | 避免测试后门变成生产后门 |

> 建议增加两个环境变量：`REGISTRATION_OPEN`（默认 `false`）与 `INVITE_SIGNUP_ENABLED`（默认 `true`）。完全关闭注册 = 两者都 `false`。均为启动时读取，改完需重启；管理台只读展示，不提供运行时开关，避免误开。

### 3.5 邀请码与网关的关系 / 绕过风险

| 层 | 保护什么 | 不保护什么 | 撤销方式 | 失效后的后果 |
|---|---|---|---|---|
| **A. 网关 Basic Auth** | 整个站点（页面、`/api`、注册、登录） | 应用内身份、账号权限、会话 Cookie 内容 | 从 Caddy 用户列表移除 + reload | 未移除的凭据仍可进入；已登录 Cookie 单独不足以通过网关 |
| **B. 应用邀请码** | 新账号创建 | 已有账号登录、游客使用 | 撤销邀请码 | 已注册账号不受影响；需要封禁/删会话才能停用 |
| **C. 应用登录** | 账号身份 | 网关层访问 | 封禁、删会话、改密 | 只挡应用，不挡站点 |

**主要绕过/失效路径：**

1. **直接调 `/api/auth/signup`**：不能只靠前端隐藏。服务端必须独立校验 `REGISTRATION_OPEN` 与邀请码；网关在时仍受 A 层保护。
2. **游客模式**：当前 `/api/*` 允许游客访问，游客有更紧限速与 `GUEST_MAX_TRANSLATED_VIDEOS=1`。网关挡住站外后，只有持网关凭据的人能成为游客；但仍要保留游客限额，防止“有网关凭据的人”无限刷 AI。
3. **网关凭据共享/转卖**：A 层是共享或按人发放的 HTTP 凭据，无法阻止转卖。B 层邀请码只能降低“拿到凭据就能批量注册”的风险；不能阻止已有账号被共享。
4. **邀请码转卖/分享**：邀请码是一次性/限次；但拿到码的人仍需要网关凭据。若进入 G2 移除网关，邀请码就是唯一门槛，必须限次、限时、审计。
5. **直接 IP 访问 / 未知 Host**：必须只暴露 80/443，uvicorn 绑定 `127.0.0.1`；Caddy 对未知 Host 不应回退到无认证站点。若使用 Cloudflare，注意灰云/橙云与源站暴露。
6. **健康检查豁免**：若为监控放行 `/healthz`，它就成为无认证入口。建议监控在服务器本机 `127.0.0.1:8000` 探活，不对外豁免；或给监控单独网关账号。
7. **会话 Cookie 30 天**：G1 期间即使移除网关账号，浏览器缓存的 Basic Auth 可能仍在下次请求自动带上；应用会话也可能仍有效。撤销访问必须“网关移除 + 应用封禁/删会话”双做。
8. **管理员路径**：`/api/admin/*` 仍需登录 + `ADMIN_EMAILS` 校验；Basic Auth 不能替代管理员身份。不要把管理员账号发给测试用户。
9. **日志/截图泄露**：网关密码、邀请码明文、Cookie 不得进仓库、日志、截图、工单。邀请码只在生成响应中出现一次。

### 3.6 G1 → G2 切换（高层，不是上线步骤）

- 前置：G2 评审通过；邮箱验证/找回方案或“持续邀请码 + 人工找回”方案已定；监控/告警/备份已验证。
- 顺序建议：准备两套 Caddy 配置（G1 带 `basic_auth`，G2 不带）→ 在维护窗口内切换应用开关与网关 → 验证首页、注册、登录、SSE、健康检查 → 保留回滚配置。
- 回滚：恢复 G1 配置 + `REGISTRATION_OPEN=false` + reload/restart；已注册用户不受影响。
- **本轮不写具体命令与步骤**；M7 之后单独交付。

### 4.3 删除数据方案

#### 4.3.1 用户如何申请

1. **登录状态下（推荐）**：账号页 → “删除账号” → 阅读影响说明 → 输入密码 + 输入用户名 + 输入 `DELETE` → 提交。
2. **无法登录（忘记密码/邮箱不可用）**：用注册邮箱向支持邮箱发信，主题 `[删除账号] <注册邮箱>`；正文写用户名、注册大致月份、最近学习内容（如最近一个视频/文章），用于人工核验。
3. **管理员不得代替用户发起删除**，除非有明确书面请求、法律要求或滥用处置；管理员发起的删除必须记录原因与证据。

#### 4.3.2 身份确认（无邮箱验证的边界）

| 场景 | 确认方式 | 强度 | 说明 |
|---|---|---|---|
| 登录状态删除/导出 | 有效会话 + 重新输入密码 + 输入用户名 + 二次确认 | 中 | 会话被盗时仍可能被操作；密码是第二因子 |
| 忘记密码，申请删除/导出 | 注册邮箱发信 + 用户名 + 注册月份 + 最近学习内容 + 人工判断 | 弱 | 无邮箱验证，无法证明邮箱归属；可疑时拒绝或要求更多信息 |
| 管理员协助 | 管理员核对请求与账号信息，记录 `verified_via=support_manual` | 弱–中 | 仅个人运营下的人工兜底；不得批量、不得跳过记录 |

**必须写进文案的边界**：本轮没有邮箱验证，因此“用注册邮箱发信”不等于“证明你是邮箱主人”；我们只能按现有信息人工判断，可能拒绝，也可能无法恢复账号。

#### 4.3.3 立即停用 / 冷静期

建议默认 **7 天冷静期**（D-1 拍板）：

```
active
  └─ 用户提交删除（密码+用户名+DELETE）
       → deletion_pending（立即生效）
          - 立即吊销全部会话（delete_user_sessions）
          - 停止 AI 调用、停止写入学习数据
          - 保留登录能力，仅用于“取消删除/导出数据”
          - 页面显示到期日与“取消删除”入口
       → 7 天后（管理员/定时任务执行）
          → deleted（硬删除）
       → 用户点击取消（登录 + 密码）
          → active（恢复；记录审计）
```

- **立即停用**：提交成功即停 AI 与写操作，不等 7 天；避免“提交后还在花钱/写数据”。
- **冷静期**：给误操作/被盗号留出反悔窗口；期间登录只允许访问 `/api/auth/*`、`/api/account/*`，其他 `/api/*` 返回 403 `account_pending_deletion`。
- **登录必须放行 `deletion_pending`**：登录路由不能直接 403，否则用户无法回来取消/导出；登录成功后在中间件按状态限制可访问路径即可。
- **到期执行**：建议由管理员在后台确认执行，或由每日定时任务执行；执行前再次检查状态仍为 `deletion_pending`。
- **不可恢复确认**：硬删除前页面/管理台明确写“不可恢复；备份中最长残留 30 天”；用户必须再次输入 `DELETE`（管理员执行时也需确认）。
- **立即硬删**：默认不提供；若用户明确书面要求，管理员可在二次确认后提前执行，仍需记录“用户主动要求立即删除”。

#### 4.3.4 删除范围（硬删除时）

> 原则：**能定位到 user_id 的行/文件全删；公共缓存不误删；备份按保留期自然过期；删除失败要可诊断、可重试，不能假装成功。**

| 对象 | 处理 | 备注 |
|---|---|---|
| `users` | 删除该行 | 最后一步；失败则整体标记 failed |
| `sessions` | 删除该用户全部会话 | 先做，立即断线 |
| `credit_transactions`（旧） | 删除该用户行；保留一条无 PII 的汇总到删除审计 | 旧表是历史演示流水，不折算 |
| `account_ledger` / `credit_holds` | 删除该用户行 | 新流水；删除审计只留总额/条数 |
| `ai_usage` / `ai_quota` | 删除该用户原始行；删除审计保留 calls/tokens/cost 汇总（无 user_id） | 账本不存 prompt；保留汇总用于容量核算 |
| `learning_events` | 按 `user_id` 与 `pseudonym_id` 删除 | 事件表最终只靠 pseudonym 归属；当前明文+假名并存 |
| `watch_events` / `weekly_reports` | 删除该用户行 | 游客归属 `guest:<hash>` 的也要按已知 guest 处理 |
| `word_states` / `review_logs` / `word_sources` | 先删 `word_sources`（按 word_state），再删 `review_logs`、`word_states` | 不能只依赖 FK 级联；显式按 id 删 |
| `content_items` / `attempts` | 删除该用户行 | `questions` 若为公共题库则保留；若由用户内容生成，按 content_ref 清理 |
| `exam_sessions` / `exam_answers` | 先按 session 删 answers，再删 sessions | `exam_answers` 无 user_id，靠 session 关联 |
| `placement_sessions` / `placement_answers` / `user_profiles` | 先按 session 删 answers，再删 sessions、profile | 同上 |
| `assessment_sessions` | 删除该用户行 | 含 guest 归属的也按 id 处理 |
| `skill_evidence` / `user_skill_profiles` | 删除该用户行 | 能力证据 |
| `articles` / `article_progress` / `article_translations` | 删除用户文章与进度；译文按 article_id 删 | 公共文章/译文不误删 |
| `imported_books` / `imported_book_translations` | 删除用户书与译文；删除 `data/users/<id>/imported-books/` | 用户上传的 EPUB 属于个人文件 |
| `course_attempts` / `course_events` | 删除该用户行 | `generated_courses` 公共课程缓存保留 |
| `jobs` / `discover_queries` | 删除该用户行 | 进行中的任务先取消/标记 |
| `content_teaching_analysis` | **需开发确认**：当前以 `content_ref` 为键，本地视频用 `local-video:<hash>`，没有 user_id | 若无法定位到用户，不能误删公共缓存；建议后续为本地视频缓存记录 `created_by` 或不做用户级删除，并在隐私政策说明 |
| `data/users/<id>/` | 整目录删除 | history、imported-books、favorites、subscriptions、dictionary_cache、.upload-staging |
| `data/exports/<id>/` | 删除该用户导出临时文件 | 过期文件也由清理任务删 |
| `data/guests/<hash>/` | 仅删除已确认属于该用户的游客目录 | 认领后通常已删除；无映射则不猜 |
| `data/subtitles/`、`data/ecdict.db`、`history/` 旧目录 | 不随单用户删除 | 公共内容/旧匿名回落数据；`history/` 不含 user_id |
| 备份 | 不单独删除；按 7 日 + 离机 30 天自然过期 | 删除后最长残留 30 天；文案必须披露 |
| 日志 | 不追溯删除；按 14–30 天轮转 | 访问日志含 user_id，但不含 body/Cookie/密码 |
| 删除审计 | 保留最小记录：`user_id_hash`、时间、方式、操作员、删除计数、成功/失败 | 不留邮箱、IP、学习内容 |

**删除后验证**：`users` 无行、`sessions` 无行、`data/users/<id>/` 不存在、管理员按 id 查不到、用旧 Cookie 请求 `/api/auth/me` 返回游客态、旧密码登录 401。任何一步失败都标记 `failed`，不得显示“已删除”。

#### 4.3.5 管理员操作与审计

- 管理台新增“删除请求”列表：用户、申请时间、到期时间、状态、操作。
- 操作：`查看`、`取消`（仅用户可取消；管理员不应代取消）、`立即执行`（二次确认 + 原因）、`标记失败`。
- 需要新增 `admin_audit_log`：谁、何时、对谁、做了什么、request_id、结果；管理员调余额、封禁、邀请码生成/撤销、删除执行都写。
- 删除审计表 `account_deletion_requests`：保留 `user_id_hash` 而不是明文 id；完成后不保留邮箱/用户名。
- 所有删除操作必须在 Feishu 发一条 P1 通知（成功/失败），便于单人运营留痕。

#### 4.3.6 备份与“删除不可逆”

- 备份归档包含 `app.db` 与 `data/users/`；历史备份中的个人数据无法按用户选择性删除（除非整包重写，成本高且影响其他用户）。
- 建议保留：每日 7 份 + 离机副本 30 天；删除后最长 **30 天**残留（D-2 拍板）。
- 隐私政策必须写清楚：“删除后，历史备份中的副本会在备份保留期到期后消失；我们不会为单个删除请求重写全部备份。”
- 如果法律/监管要求更短，需单独评估；本轮不承诺“立即从所有备份消失”。

### 4.4 导出数据方案

#### 4.4.1 触发方式

- 登录状态下：账号页 → “导出我的数据” → 输入密码 → 提交。
- 忘记密码：按 §4.3.2 人工核验后，由管理员触发导出；不通过邮件发送文件（无邮件服务），只提供一次性下载链接/临时文件路径，由管理员转交。
- 导出不改变账号状态；可在 `deletion_pending` 期间导出。

#### 4.4.2 导出内容清单

| 分组 | 内容 | 格式 |
|---|---|---|
| 账号 | id、email、username、created_at、status、余额（µUSD 与 USD 字符串） | `profile.json` |
| 余额/流水 | `account_ledger` 全部行（不含他人）、旧 `credit_transactions` 只读快照 | `billing.json` |
| AI 用量 | 按 feature/model/日汇总 + 每次调用明细（不含 prompt；含 tokens/成本/价格版本） | `ai-usage.json` |
| 学习记录 | history 缓存、favorites、subscriptions | `learning/*.json` |
| 复习 | word_states、review_logs、word_sources | `review.json` |
| 观看/周报 | watch_events、weekly_reports | `activity.json` |
| 理解题/考试 | content_items、attempts、exam_sessions/answers | `practice.json` |
| 定位/能力 | placement/assessment/profile/evidence | `assessment.json` |
| 阅读 | articles、article_progress（不含公共译文） | `reading.json` |
| 导入书 | imported_books 元数据 + 用户上传的 EPUB 文件 | `books/` |
| 课程 | course_attempts、course_events | `courses.json` |
| 说明 | 字段说明、生成时间、数据范围、排除项 | `README.md` + `manifest.json` |

**排除**：密码哈希、会话 token、Cookie、他人数据、管理员备注、内部日志、模型 prompt（当前不存）、公共缓存/词典、备份文件。导出文件不包含任何可直接登录的凭据。

#### 4.4.3 格式与流程

- 格式：ZIP；根目录 `manifest.json`（版本、生成时间、用户 id 哈希、文件清单、SHA256）、`data/*.json`、`files/`、`README.md`。
- 流程：
  1. `POST /api/account/export` 校验密码/限流 → 创建 `data_export_jobs`（status=`queued`）。
  2. 后台任务生成 ZIP 到 `data/exports/<user>/<job>.zip`；大小上限建议 200 MB；超过则失败并提示联系管理员。
  3. 生成一次性下载 token（32 字节随机，库内只存 sha256）；`GET /api/account/export/{jobId}` 凭会话 + token 下载。
  4. 文件 24 小时后过期；下载成功后可立即删除；每小时清理过期文件。
- 频率：1 次/24 小时、3 次/30 天；同一用户同时只允许 1 个进行中的导出（D-5 拍板）。
- 密码确认失败：401/403 统一文案，不区分“密码错”与“用户不存在”；失败计入限流。
- 导出任务状态：`queued/running/ready/failed/expired`；站内显示，不发邮件。

#### 4.4.4 导出 API 草案

| 方法 | 路径 | 认证 | 请求 | 成功 | 失败 |
|---|---|---|---|---|---|
| POST | `/api/account/export` | 登录 + 密码 | `{password}` | 202 `{jobId,status,expiresAt}` | 401 密码错；409 已有任务；429 限流 |
| GET | `/api/account/export/{jobId}` | 登录 + 一次性 token | query `token` | 200 `application/zip` | 403/404/410 过期 |
| GET | `/api/account/exports` | 登录 | — | 列表（脱敏，不含 token） | — |
| DELETE | `/api/account/export/{jobId}` | 登录 | — | 删除临时文件 | 404 |

### 4.5 不接邮箱的边界与文案

**必须让用户在注册前看到：**

1. 我们不会发送验证邮件；请使用你能长期控制的邮箱。

## 5. 余额与成本

### 5.1 现状（代码事实）

- `users.credits` 是 `INTEGER NOT NULL DEFAULT 0`；`account.adjust_credits()` 只允许管理员调账，`BEGIN IMMEDIATE` 原子更新 + 追加 `credit_transactions`；不允许扣成负数；范围 ±100,000（旧单位）。
- **没有任何 AI 扣费逻辑**：AI 功能只受 `ai_quota` 功能日配额 + 用户日预算 + 全站日预算约束；`credits` 不参与调用拦截。
- `ai_usage` 每成功调用一条：`user_id/feature/model_id/provider/input_tokens/output_tokens/calls/est_cost_usd/occurred_at/created_at/usage_date/target_lang`；`est_cost_usd` 是 `Float`，写入时按目录价计算。
- `ledger.price_for()` 对缺价模型按“目录里已知最贵”的 in/out 计；目录完全没有已知价时用兜底价 `$3.00/$15.00 per 1M tokens`（代码常量，非官方报价）。
- 现有默认闸门（`config.py`）：用户日预算 `AI_DAILY_BUDGET_USER_USD=1.0`、全站日预算 `AI_DAILY_BUDGET_GLOBAL_USD=20.0`；功能日配额如翻译 60 批、总结 10 次、词典 200 次、本地剧集 60 批、理解题 30 次等。**$2.00 是总额余额，日预算是每日上限，两者独立**；按默认 $1.00/天，$2.00 至少够两天，但单日仍受 $1.00 限制。不要为了“花完 $2”把日预算直接改成 $2；应在文案里区分“今日额度”和“账户余额”。
- `llm._record_usage()` 在 provider 没回 usage 时按“2 字符/token”估算，并只记 debug 日志；`record_usage` 没有 `token_source`/`price_version`/`billable` 字段。
- 当前 `MODEL_CATALOG` 价格：只有 `gemini-2.5-flash` 有代码值 `in=0.30 / out=2.50 USD per 1M tokens`（未按官方页复核）；其余 5 个模型均为 `None`。
- 本机 `data/app.db` 现有 883 条 `ai_usage`，合计 `est_cost_usd=2.4644`；这些是“缺价按 Gemini 2.5 Flash 上限”的估算，不是厂商账单。

### 5.2 金额单位与数据模型

**单位约定（必须写进代码注释、API 文档、管理台）：**

| 名称 | 含义 | 精度 |
|---|---|---|
| `USD` | 美元 | 展示用，字符串保留 2–6 位小数 |
| `µUSD`（micro-USD） | 1 USD = 1,000,000 µUSD = $0.000001 | 数据库整数，最小 1 µUSD |
| `USD/1M tokens` | 厂商单价 | 只在价格表/文档中使用；入库为 `micro_usd_per_mtok` 整数 |
| `token` | 模型输入/输出 token | 整数，provider 返回或估算 |
| `ms` | 毫秒时间戳（UTC） | 整数 |

**禁止**：把美元浮点直接写进 SQLite 金额列；用 `REAL` 做余额/扣费；用 `est_cost_usd` 当扣费依据。

**建议数据模型：**

1. `users` 新列 `balance_micro_usd INTEGER NOT NULL DEFAULT 0`；新用户开户写 `2,000,000`。
   - 旧 `users.credits` **冻结**：不再写、不再作为扣费依据；管理台显示为“历史演示额度（旧单位）”。不做 1:1 折算，避免凭空定义汇率。
   - 迁移时为现有用户补 `balance_micro_usd=0`；是否补发 $2.00 由 D-3 决定。
2. 新表 `account_ledger`（append-only，金额整数 µUSD）：

```sql
CREATE TABLE account_ledger (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  kind TEXT NOT NULL,                  -- signup_bonus/admin_topup/admin_deduct/ai_reserve/ai_settle/ai_refund/adjustment/legacy_snapshot
  delta_micro_usd INTEGER NOT NULL,    -- 正=入账，负=出账
  balance_after_micro_usd INTEGER NOT NULL,
  ref_type TEXT,                       -- ai_usage/hold/manual
  ref_id TEXT,
  reason TEXT,
  actor_id TEXT,                       -- 管理员/系统；用户自助为空
  idempotency_key TEXT UNIQUE,
  created_at_ms INTEGER NOT NULL
);
```

3. 新表 `credit_holds`（预占，见 §5.8）。
4. `ai_usage` 新列（可空，历史行标记 legacy）：`cost_micro_usd`、`input_price_micro_usd_per_mtok`、`output_price_micro_usd_per_mtok`、`price_version`、`price_source`、`token_source`、`billable`、`billing_status`、`hold_id`、`request_id`。
5. 新表 `model_prices`（§5.7）。
6. 旧 `credit_transactions` 保留为历史表，不再新增（或只读迁移）；新的调账/扣费全部写 `account_ledger`。管理台旧的 `POST /api/admin/users/{id}/credits` 标记 deprecated，前端改用新接口。

**兼容策略：**

- API 增加 `balanceMicroUsd`（整数）与 `balanceUsd`（字符串，如 `"2.00"`）；`credits` 字段暂时保留旧值，仅旧客户端兼容，不再参与扣费。
- 前端账户页/管理台在 M3 同步改为新字段；旧 `credits` 显示加“旧单位”说明，避免误解。
- 不在旧表上改列类型；不把旧 `credits` 直接乘 1,000,000（那会把 100 变成 $100，凭空造钱）。

### 5.3 新用户开户事务与 $2.00 默认余额

**目标**：注册成功后，用户、余额、开户奖励流水、邀请码兑换记录**同一事务**提交；不能出现“用户已建、余额没发”或“邀请码已用、用户没建”。

建议流程（伪代码，未实现）：

```text
1. 校验邮箱格式/密码/用户名；Argon2 哈希密码（事务外，避免长时间锁库）
2. BEGIN IMMEDIATE
3. 校验邀请码：存在、未撤销、未过期、used_count < max_uses
4. INSERT users（balance_micro_usd = 2_000_000）
5. INSERT account_ledger（kind=signup_bonus, delta=+2_000_000, balance_after=2_000_000）
6. INSERT invite_redemptions；UPDATE invite_codes SET used_count=used_count+1
7. INSERT sessions（token 先在外生成；库内存 hash）
8. COMMIT
9. Set-Cookie；返回 user + balance
```

- 配置 `SIGNUP_BONUS_MICRO_USD=2000000`（默认 $2.00），只在一个地方定义；测试可设 0。
- 如果 `account_ledger`/`invite_codes` 表缺失（未迁移）：注册返回 503，**不降级为“先建用户后补余额”**；G1 上线前必须迁移。
- 如果会话插入失败：回滚整个事务；用户可重新注册（邀请码未被占用）。
- 邀请码消耗与用户创建同事务；邮箱冲突回滚，不消耗邀请码。
- 现有用户是否补发：D-3。建议一次性补发所有 active 账号 $2.00，写 `kind=signup_bonus_backfill`，可审计；已封禁/已删除不补。

### 5.4 管理员手动充值 / 扣减

**入口**：管理台用户详情 → “调整余额”。

- 输入：金额（美元字符串，最多 6 位小数，如 `"2.00"`）、方向（增加/扣减）、原因（1–200 字）、幂等键（前端生成 UUID）。
- 服务端把美元字符串精确转成 µUSD（避免 JSON 浮点）：`"2.00"` → `2000000`；拒绝超过 6 位小数。
- 校验：非 0；单次上限建议 ±$100.00（`100,000,000 µUSD`）；扣减后不得为负；用户存在；管理员身份。
- 事务：`BEGIN IMMEDIATE` → 读余额 → 计算新余额 → `UPDATE users` → `INSERT account_ledger`（`kind=admin_topup/admin_deduct`，`balance_after`）→ commit。
- 幂等：`idempotency_key` 唯一；重复请求返回原结果，不重复加钱。
- 审计：`admin_audit_log` + 飞书 P1 通知；记录操作者、金额、原因、前后余额。
- 旧 `adjust_credits`：保留只读兼容或返回 410；不再用旧单位调账。

### 5.5 余额不足 402 / 配额 429 语义

| 状态码 | 含义 | 触发 | 用户动作 | 响应要点 |
|---|---|---|---|---|
| **402 Payment Required** | 账户余额不足（或为负） | 预占时 `available < required` | 联系管理员充值 | `code=insufficient_balance`、`balanceMicroUsd`、`requiredMicroUsd`、`topup=admin` |
| **429 Too Many Requests** | 日配额/日预算/限流 | 功能配额、用户日预算、全站日预算、登录/注册限流 | 明天再试或按 `Retry-After` | `code=quota_exceeded/budget_exceeded/rate_limited`、`Retry-After` |
| **403 Forbidden** | 封禁/待删除/无权限 | `status=banned/deletion_pending`、非管理员 | 联系管理员 | `code=account_disabled/account_pending_deletion/admin_required` |
| **401 Unauthorized** | 未登录/密码错 | 会话无效、密码错误 | 重新登录 | 不泄露账号是否存在 |

**检查顺序（建议）**：认证 → 限流 → 余额可用性（402）→ 日预算/功能配额（429）→ 预占。若余额为 0 且日预算也已用尽，优先返回 402（用户可行动）；全站预算耗尽优先 429（系统保护）。

**前端要求**：`apiFetch` 统一映射 402/429，不显示“服务器错误”；账户页显示余额、今日用量、充值请联系管理员的说明；管理台显示用户余额与最近流水。

### 5.6 每次 AI 调用的成本记录

**目标字段（写入 `ai_usage`，每次成功调用一行）：**

| 字段 | 示例 | 说明 |
|---|---|---|
| `request_id` | `01J...` | 关联访问日志/排查 |
| `hold_id` | `hold_...` | 预占记录 |
| `feature` | `translate` | 现有枚举 |
| `model_id` / `provider` | `deepseek-chat` / `DeepSeek` | 实际调用的模型，不是首选 |
| `input_tokens` / `output_tokens` | `1234` / `567` | 整数；provider 返回 |
| `token_source` | `provider/estimated/mixed` | 估算时必须标记 |
| `input_price_micro_usd_per_mtok` | `300000` | 整数 µUSD / 1M tokens |
| `output_price_micro_usd_per_mtok` | `2500000` | 同上 |
| `price_version` | `2026-11-20.official.1` | 价格快照版本 |
| `price_source` | `official/catalog_unverified/ceiling_unknown/vendor_bill` | 来源 |
| `cost_micro_usd` | `1234` | 最终成本，整数 µUSD；四舍五入规则见下 |
| `est_cost_usd` | `0.001234` | 兼容字段，由 `cost_micro_usd/1e6` 派生，仅供分析 |
| `billable` | `1/0` | 是否可扣用户余额；缺价模型为 0 |
| `billing_status` | `settled/unbilled/legacy` | 计费状态 |
| `occurred_at` / `usage_date` | ms / `2026-11-20` | 现有口径 |

**计算**：

```text
cost_micro = ceil(input_tokens * in_micro_per_mtok / 1_000_000)
           + ceil(output_tokens * out_micro_per_mtok / 1_000_000)
```

- 每个分量向上取整到 1 µUSD；单次最多多收 1 µUSD/分量。理由：宁可略高估，不把成本记成 0。
- 如果实际调用模型与预占模型不同（降级链切换），按实际模型价格结算；预占按候选链最高价，保证不超。
- 如果 provider 没回 usage：按字符估算（当前 `_estimate_tokens` 是 `len//2`，偏保守），`token_source=estimated`；仍记账但标记“估算”，对账时单独统计。
- 如果模型缺价：`cost_micro_usd=NULL` 或按上限估算但 `billable=0`、`price_source=ceiling_unknown`；**不得静默写 0**。

```sql
  id TEXT PRIMARY KEY,
  model_id TEXT NOT NULL,
  provider TEXT NOT NULL,
  effective_from_ms INTEGER NOT NULL,
  input_micro_usd_per_mtok INTEGER NOT NULL,
  output_micro_usd_per_mtok INTEGER NOT NULL,
  source_kind TEXT NOT NULL,           -- official_page/vendor_bill/manual
  source_ref TEXT,                     -- 官方价格页 URL 或账单编号（可公开的才入库）
  verified_at_ms INTEGER NOT NULL,
  price_version TEXT NOT NULL,
  note TEXT
);
```

2. 每个模型同一时间只有一条 active 价格（按 `effective_from_ms` 取最新）；历史行保留，不覆盖。
3. `MODEL_CATALOG` 继续负责“模型是否存在/可用/Key/端点”，价格改由 `model_prices` 解析；`MODEL_CATALOG` 的 `in/out` 仅作离线兜底，且标记 `catalog_unverified`。
4. 价格版本格式：`YYYY-MM-DD.<source>.<seq>`，例如 `2026-11-20.official.1`；每次改价新增版本，不改历史。
5. 补价优先级：`deepseek-chat`（默认）→ `qwen-flash`（越南语默认）→ `gemini-2.5-flash` 复核 → `qwen-plus` → `gemini-3.5-flash-lite` / `gemini-3.1-pro-preview`（若继续启用）。
6. 价格来源必须记录：官方价格页（截图/URL + 核对日期）或厂商账单；不要凭印象填数字。价格是否含税、币种、阶梯/缓存/批处理折扣都要在备注中写清。
7. 未补齐的模型：`billable=0`，不扣用户余额；`BILLING_STRICT=1` 时从计费降级链中排除，避免“免费调用未定价模型”。

### 5.8 扣费时点、预占、结算、失败回滚、并发

**原则：调用前预占，调用后按真实用量结算；失败回滚；任何一步都不能把余额扣成“说不清”。**

#### 5.8.1 预占（reserve）

- 触发：每次真正要调用模型前（翻译一批、总结、查词、分析、出题等），在现有 `quota.check_and_consume_quota()` 附近增加余额预占。
- 预占金额：
  - 输入 token 估算：prompt 字符数/2（保守）或 tokenizer；输出按该功能 `MAX_OUTPUT_TOKENS`。
  - 单价：候选降级链中**最高**的 in/out 价（防止切到更贵模型时超支）；缺价模型按已知上限。
  - 加 20% 安全边际；最小 1 µUSD；单次预占上限建议 `$0.50`（超过则拒绝并提示联系管理员，避免一次长任务占满余额）。
- 原子性：`BEGIN IMMEDIATE` 内计算 `available = balance_micro_usd - SUM(active holds)`；若 `available < reserve` → 回滚 → 402；否则插入 `credit_holds`。
- 不在预占时写 `account_ledger`（余额表不变；可用余额由 hold 扣减），这样“账面余额”和“可用余额”可区分。账户页/管理台显示 **可用余额**；对账脚本用账面余额 + 流水校验。

#### 5.8.2 结算（settle）

- 模型返回后，读取 provider usage（或估算），计算 `cost_micro_usd`；写 `ai_usage`。
- `BEGIN IMMEDIATE`：
  - 读 hold；若已过期/已释放 → 记录异常（可能重复结算），不再扣；
  - `balance_micro_usd -= actual`；若 actual > hold（估算偏差/价格变化）→ 允许账面为负但记录 `overrun`，下一次调用 402；不得少记；
  - `INSERT account_ledger(kind=ai_settle, delta=-actual, balance_after)`；
  - `UPDATE credit_holds SET status='settled'`。
- 若 actual < reserve：差额自动释放（hold 删除/标记 settled），余额只扣 actual；不需要额外退款流水。
- **结算写入不能是 best-effort**：现有 `ledger.record_usage()` 失败只记日志并返回 `None`，适合“分析账本”，不能直接用于扣费。计费路径必须：先落结算/扣费，再返回模型结果；结算失败则保留 hold 为 `active`、告警、下次重试，绝不能静默丢失扣费。可以复用 `record_usage` 但增加 `raise_on_failure=True` 的严格模式，或单独写 `settle_billing()`。

#### 5.8.3 失败回滚（release）

- 调用失败/超时/取消：`UPDATE credit_holds SET status='released'`；不扣余额；写 `ai_usage` 失败记录（可选，`billing_status='failed'`，`cost=0`，不扣费）。
- 注意：provider 可能已经计费但没返回 usage；我们无法知道。这种“不可见计费”只能靠厂商账单对账，见 §5.9。
- 流式中断：已结算的批次保留；当前批次的 hold 释放；未开始的批次不预占。

#### 5.8.4 并发与崩溃

- SQLite 单写进程：所有余额/预占/流水写操作使用 `BEGIN IMMEDIATE`，不用“先 SELECT 再 UPDATE”的无锁读改写。
- 唯一约束：`credit_holds.id`、`account_ledger.idempotency_key`；重复结算/重复充值用幂等键拒绝。
- 崩溃恢复：`credit_holds` 有 `expires_at_ms`；后台清理任务把超过 30 分钟仍 `active` 的 hold 标记 `expired` 并释放；记录日志/告警。已扣未结算的调用可能丢失 `ai_usage`，对账时按厂商账单补差。
- 并发调用：同一用户多标签页/多请求时，`available` 计算包含其他 active holds，避免“同时看到 $2.00 都通过”。
- 资金安全：任何余额变更都必须有 `account_ledger` 行；`SUM(delta_micro_usd)` 应等于 `balance_micro_usd`（可加日对账脚本校验）；不一致告警。

#### 5.8.5 预占大小示例（仅说明单位，不是报价）

假设某批输入估算 2,000 tokens、输出上限 1,000 tokens，候选链最高价按当前目录已知上限（Gemini 2.5 Flash：300,000 / 2,500,000 µUSD per 1M）计算：

```text
输入：2000 * 300000 / 1e6 = 600 µUSD
输出：1000 * 2500000 / 1e6 = 2500 µUSD
小计：3100 µUSD = $0.0031
加 20%：3720 µUSD；取整到 3720 µUSD
```

> 实际价格补齐后重算；这里只演示“整数 µUSD”的算法，不是厂商报价。

### 5.9 “尽量准确”能做到什么、做不到什么

| 误差来源 | 影响 | 处理 | 残余风险 |
|---|---|---|---|
| 模型缺价 | 无法知道真实单价 | 补价前 `billable=0`；不扣余额；记录上界 | 用户用量无法计费；$2.00 暂时不生效 |
| provider 未返回 usage | token 数不准 | 按字符估算并标 `estimated`；对账单列 | 可能高估/低估 |
| 缓存/批处理/阶梯/夜间折扣 | 厂商账单低于标价 | 按标价记录；不模拟折扣 | 账本高于账单 |
| 失败/超时但厂商已计费 | 账本漏记 | 记录失败；月度账单对账 | 无法逐笔归因 |
| 价格调整 | 历史成本不可比 | `price_version`；不改历史 | 跨版本比较需说明 |
| 币种/税/汇率 | 账单含税/其他币种 | 统一 USD 不含税；备注 | 与财务口径差异 |
| tokenizer 差异 | token 估算偏差 | 优先 provider usage；估算标记 | 小偏差 |
| 四舍五入 | 每分量 ≤1 µUSD | 向上取整 | 可忽略 |

**结论**：对“有官方价 + provider 返回 usage”的模型，可以做到**可复核的逐次成本**；对缺价、估算、失败调用，只能做到“上界/近似”，不能承诺绝对准确。G2 前必须至少补齐默认模型价格，并完成一次厂商账单对账；否则 `$2.00` 余额只是展示，不是可靠的成本控制。

**对账建议**：每日按 provider/model 汇总 `cost_micro_usd` 与 token 数；每月与厂商账单对比；记录差异原因；差异 >5% 或出现未知价调用时告警并暂停计费（D-4）。

## 6. 邀请码设计

### 6.1 目标与原则

- 一人一码/限次；默认 1 次、30 天有效；可撤销；可审计。
- 服务端只存哈希，明文只在生成响应中出现一次；日志/数据库/备份都不出现明文。
- 注册校验与用户创建、余额发放、兑换记录同事务；并发下不超发。
- 管理台可生成/查看/撤销/看兑换；不提供“明文找回”。
- 与 `REGISTRATION_OPEN` 解耦：邀请码在 G1 必需，G2 可选。

### 6.2 表结构草案

```sql
CREATE TABLE invite_codes (
  id TEXT PRIMARY KEY,
  code_hash TEXT NOT NULL UNIQUE,      -- HMAC-SHA256(pepper, normalized_code)
  code_prefix TEXT NOT NULL,           -- 前 4–6 位，仅供管理台辨认
  created_by TEXT NOT NULL,            -- 管理员 user id
  created_at_ms INTEGER NOT NULL,
  expires_at_ms INTEGER,               -- NULL = 不过期（不建议）
  max_uses INTEGER NOT NULL DEFAULT 1,
  used_count INTEGER NOT NULL DEFAULT 0,
  revoked_at_ms INTEGER,
  revoked_by TEXT,
  note TEXT,
  last_used_at_ms INTEGER
);

CREATE TABLE invite_redemptions (
  id TEXT PRIMARY KEY,
  code_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  email TEXT NOT NULL,                 -- 兑换时快照；仅管理员可见
  redeemed_at_ms INTEGER NOT NULL,
  ip_hash TEXT,                        -- 可选，盐化；默认不存，减少 PII
  UNIQUE(code_id, user_id)
);
```

> 不存明文、不存可逆加密；`code_prefix` 只用于人工辨认，不能用于登录。

### 6.3 生成规则

- 码格式：`LN-XXXXX-XXXXX`（前缀 `LN-` + 10 位 Crockford Base32，去掉 `I/L/O/U` 等易混字符；归一化时转大写、去空格/连字符）。
- 熵：10 位 × 5 bit ≈ 50 bit；建议 12 位（60 bit）更稳；具体长度实现时定，不低于 50 bit。
- 生成：`secrets.token_bytes` / `secrets.choice`，不用 `random`；服务端生成，客户端不参与。
- 哈希：`HMAC-SHA256(INVITE_CODE_PEPPER, normalized_code)`；`INVITE_CODE_PEPPER` 只在服务端 env，不进仓库；轮换会使旧码全部失效，需提前公告。
- 明文只在 `POST /api/admin/invites` 响应中出现一次；前端提供“复制”按钮；关闭弹窗后不可再取。
- 管理台列表只显示 `code_prefix`、创建者、时间、状态、用量；不显示完整码。

### 6.4 次数 / 过期 / 撤销

| 字段 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `max_uses` | 1 | 1–10 | G1 一人一码；团队码可 >1，但需备注 |
| `expires_at_ms` | 30 天 | 1–90 天 | 到期后不可用；过期不自动删除，保留审计 |
| `revoked_at_ms` | NULL | — | 撤销立即生效；已注册账号不受影响 |
| `used_count` | 0 | 0–max | 原子递增；不可回退 |
| 状态 | 可用 | 可用/已用完/已过期/已撤销 | 由字段计算，不单独存 |

- 撤销后：注册返回 403 统一文案；管理台显示“已撤销”；已兑换记录保留。
- 过期清理：不删除；列表可按状态筛选；备份含哈希，不含明文。
- 重新生成：旧码不复活；生成新码。

### 6.5 管理员 UI / API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/invites` | `{count=1, expiresInDays=30, maxUses=1, note}` → `{codes:[{id,code,prefix,expiresAt,maxUses}]}`（明文仅此一次） |
| GET | `/api/admin/invites?status=&limit=&offset=` | 列表；不返回明文/哈希 |
| POST | `/api/admin/invites/{id}/revoke` | 撤销；幂等 |
| GET | `/api/admin/invites/{id}/redemptions` | 兑换记录（邮箱、用户 id、时间） |
| GET | `/api/admin/invites/summary` | 可用/已用/过期数量，给仪表盘 |

**管理台页面**：邀请码 tab；生成对话框；列表；撤销确认；兑换记录抽屉；空态/错误态/加载态；复制后提示“只显示一次，请立即保存”。

### 6.6 注册校验流程（原子）

1. 归一化 `inviteCode`（大写、去空格/连字符）；空 → 403 `invite_required`（当 `REGISTRATION_OPEN=false`）。
2. 计算 HMAC；`BEGIN IMMEDIATE`。
3. `SELECT ... FROM invite_codes WHERE code_hash=?`；不存在/撤销/过期/`used_count>=max_uses` → 回滚 → 403 统一文案。
4. 校验邮箱格式/密码/用户名（事务外已完成部分）；检查邮箱唯一（唯一约束兜底）。
5. 创建用户 + $2.00 余额 + 流水 + 邀请兑换 + `used_count+1` + 会话；commit。
6. 任何唯一冲突（邮箱/兑换）回滚，邀请码不消耗。
7. 失败原因只写服务端审计/日志（不含明文码），对外统一文案。

**顺序注意**：Argon2 哈希密码较慢，放在事务外；事务内只做短写操作，避免锁库过久。

### 6.7 限流与防爆破

- 注册：建议 5 次/小时/IP、20 次/天/IP；失败邀请码 10 次/小时/IP；全局 100 次/天（可按内测规模调）。
- 登录已有 10 次/60s/IP + 账号/IP 锁定；沿用。
- 网关 Basic Auth 自身也可加 rate limit（Caddy 层，未实现）；应用层不能依赖网关。
- 邀请码熵 ≥50 bit，暴力枚举不可行；限流主要防撞库/脚本。
- 不在响应中区分“码不存在/已过期/已撤销/已用完”；服务端审计记录真实原因。
- 注册 409“邮箱已注册”会泄露邮箱存在；G2 前评估是否改统一响应。G1 可接受，但需在隐私政策说明。

### 6.8 审计

- 生成/撤销写 `admin_audit_log`：actor、action、code_id、count、expiry、request_id、时间。
- 兑换写 `invite_redemptions`；用户删除后，兑换记录按删除策略处理（保留 `code_id` + 时间，不留邮箱/用户 id 明文）。
- 明文码不写日志；如果管理员复制失败，只能重新生成。
- 飞书 P1 通知：批量生成/撤销、异常失败率、兑换激增。

## 7. 网关 Basic Auth

### 7.1 配置位置

- VPS 裸机：`deploy/Caddyfile` 的站点块内，`ln.example.com { ... }`。
- Docker：`deploy/Caddyfile.proxy` 的站点块内（容器内已做静态/SPA，宿主机 Caddy 只做 TLS + 反代）。
- 生产实际配置在服务器 `/etc/caddy/Caddyfile`（或 include 的受保护文件）；**仓库里的模板不写真实用户名/密码哈希**。
- Basic Auth 必须放在站点入口，覆盖 `/`、`/api/*`、`/health*`；不要只保护登录页或某个路径。

### 7.2 账号来源与密码

- 账号列表只存在服务器本地（Caddyfile 或 `import` 的受保护文件），权限 600；不进 git、不进备份的 `config/`（备份只读 `.env` 键名，不含值）。
- 密码用 `caddy hash-password --plaintext '<password>'` 生成 bcrypt 哈希；Caddyfile 里只放哈希。
- 建议 **一人一账号**，便于撤销；不要所有人共用一个密码。10–30 人规模可管理。
- 凭据通过站外渠道单独发送；不通过邮件（无邮件服务）、不放在公开文档、不在截图/工单中出现。
- 轮换：删除用户 → reload；如怀疑泄露，全部重置并 reload；同时封禁应用账号/删会话。

### 7.3 与邀请码的双层关系

| 场景 | 网关 | 邀请码 | 结果 |
|---|---|---|---|
| 正常 G1 新用户 | 有效 | 有效 | 可注册、可登录 |
| 老用户 | 有效 | 不需要 | 可登录 |
| 网关凭据泄露 | 有效（攻击者） | 无 | 可浏览/当游客，不能注册；已有账号仍需密码 |
| 邀请码泄露 | 无 | 有效 | 进不了站（网关挡住） |
| 两者都泄露 | 有效 | 有效 | 可批量注册；只能靠限流/审计/封禁 |
| G2 后 | 移除 | 可选/不需要 | 公开注册（需另行评审） |

**关键**：两层不是“二选一”，而是**串联**。网关负责“谁能到站”，邀请码负责“谁能建号”，应用登录负责“谁是账号”。

### 7.4 健康检查、SSE、监控

- **建议不要把 `/health`/`/healthz` 对公网豁免**。监控在服务器本机 `curl 127.0.0.1:8000/healthz`，或给外部监控单独发一个网关账号；这样不会产生无认证入口。
- 若必须豁免（例如外部 uptime 服务无法带 Basic Auth），需在 Caddy 用独立 `handle`/`route` 把健康路径放在认证之外；**必须在目标 Caddy 版本 `caddy validate` 并实测 401/200**，不能照抄未验证片段。
- SSE：Basic Auth 只在建立连接时校验；Caddy `flush_interval -1` 与后端 15s 心跳保持不变。需实测浏览器长流 30 分钟、断流重连、代理超时；Basic Auth 不应导致 SSE 中断。
- 浏览器 Basic Auth 行为：首次页面导航弹窗，之后同域请求自动带凭据；`fetch` 收到 401 不一定弹窗；登出应用不会清除网关凭据。文案要说明“关闭浏览器/清除站点数据才可能退出网关”。
- `/api/admin/*` 仍需应用管理员校验；不要让网关账号 = 管理员。

### 7.5 G1 → G2 摘除（只写原则，不写操作步骤）

- 保留两份配置：`Caddyfile.g1`（含 `basic_auth`）与 `Caddyfile.g2`（不含）；生产切换时保留上一版可回滚。
- 切换前必须验证：首页、`/api/auth/registration`、注册开关行为、SSE、健康检查；验证通过才对外。
- 回滚原则：切回 G1 配置 + `REGISTRATION_OPEN=false`；已注册用户不受影响。
- **不要**在未完成 G2 评审时摘除网关；不要只改前端隐藏登录页。
- 具体命令、顺序、维护窗口、验证清单属于 M7 的“详细上线步骤”交付物，本轮不写。

### 7.6 绕过与边界风险

1. **源站暴露**：只开 22/80/443；uvicorn 绑 `127.0.0.1`；Docker 端口映射到 `127.0.0.1`；未知 Host 不应落到无认证站点；Cloudflare 橙云时确认回源只允许 Cloudflare IP（或使用 Tunnel）。
2. **缓存**：Caddy/Cloudflare 不应缓存认证响应；`/api/*` 默认不缓存；`index.html` no-cache；避免把带凭据的页面缓存给未认证用户。
3. **Cookie 边界**：网关凭据 ≠ 应用会话；Cookie 仍可能被 XSS/恶意扩展偷走；HTTPS、HttpOnly、SameSite=Lax、CSP 保持；G1 的网关层能在 Cookie 被盗时提供一层额外保护，G2 移除后没有这层。
4. **共享电脑**：Basic Auth 凭据会被浏览器缓存；用户共用电脑时可能互相进入。文案建议使用私人浏览器/退出后清除站点数据。
5. **日志**：Caddy 访问日志不应记录 `Authorization`；默认不记录；确认日志配置。
6. **密码哈希**：bcrypt 哈希可被离线破解（弱密码）；要求强密码；不要复用其他站点密码。
7. **邀请码/凭据转卖**：无法技术阻止；限次、限时、审计、封禁、法律条款禁止转卖。
8. **管理员误操作**：Caddyfile 改错会导致全站 401/无法访问；保留上一版配置与回滚；变更走维护窗口。

## 9. 飞书告警

### 9.1 目标与非目标

- **目标**：G1 期间单人运营也能在 5 分钟内知道“是否正常”；P0 事件能叫醒人；成本/备份/证书/磁盘异常有记录。
- **非目标**：不做完整 APM/Sentry/日志平台；不做多通道（短信/电话）；不做 24/7 值班；不把飞书当唯一日志存储。
- **原则**：告警在请求路径之外发送；发送失败不影响业务；密钥不进仓库；告警可去重、可静默、可降级。
- **级别**：P0 立即处理（站点不可用/数据风险）；P1 当日处理（成本/备份/证书/安全异常）；P2 每日摘要（运营/审计）。

### 9.2 架构与位置（待建）

建议两层，共用一个小模块：

1. **应用内事件钩子**（`backend/alerts.py`）：LLM 失败率、日花费、余额异常、未知价调用、管理员操作；只做计数/阈值判断，异步发送，绝不阻塞请求。
2. **外部巡检脚本**（`scripts/ops_check.py` 或 `.mjs`，由 cron 每 1–5 分钟跑）：`/healthz` 本机探活、5xx 日志计数、磁盘、证书到期、备份文件是否存在、恢复演练结果、Caddy 状态；发送飞书。
3. **发送器**：统一 `send_feishu(event, severity, dedup_key, details)`；支持签名、超时、重试、去重、dry-run、失败落盘。

> 不在本轮实现代码；M5 落地。

### 9.3 环境变量与密钥

| 变量 | 必填 | 说明 |
|---|---|---|
| `FEISHU_WEBHOOK_URL` | 是 | 自定义机器人 webhook；**本身是密钥**，只放服务器 env（600） |
| `FEISHU_WEBHOOK_SECRET` | 建议 | 签名密钥；与 webhook 一起轮换 |
| `ALERT_ENV` | 是 | `prod`/`staging`；消息里带环境，避免误判 |
| `ALERT_MIN_SEVERITY` | 否 | 默认 `P2`；测试可设 `P0` |
| `ALERT_DEDUP_SECONDS` | 否 | 默认 600 秒；同一 fingerprint 内不重复 |
| `ALERT_TIMEOUT_SECONDS` | 否 | 默认 5 秒；超时即放弃，不阻塞 |
| `ALERT_DRY_RUN` | 否 | `1` 只打印/落盘，不发网络 |
| `ALERT_DAILY_DIGEST_HOUR` | 否 | 默认 9 点；P2 每日摘要 |

- 不把 webhook/secret 写进 `Caddyfile`、前端 bundle、`docker-compose.yml`、Dockerfile、文档、截图。
- 服务器 env 文件权限 600；轮换时先加新 webhook，验证后再删旧。
- 签名（若启用）：按飞书自定义机器人规则，用 `timestamp + secret` 做 HMAC-SHA256 后 base64，请求体带 `timestamp`/`sign`；具体字段以飞书当前文档为准。secret 不落库、不进日志。
- 飞书自定义机器人可能有限流/签名要求，以飞书当前文档为准（未核实）。

### 9.4 告警事件、阈值与级别（建议）

| 事件 | 级别 | 条件（建议） | 动作 | 去重 |
|---|---|---|---|---|
| `/healthz` 503/degraded | P0 | 连续 2 次（间隔 1 分钟） | @负责人；附 version/DB/migration | 10 分钟 |
| 5xx 率异常 | P0 | 5 分钟内 ≥5 次或 ≥1% | 附最近错误摘要/request_id | 10 分钟 |
| 登录/注册全挂 | P0 | 认证端点 5xx 连续 3 次 | 附状态码 | 10 分钟 |
| LLM 失败率高 | P1 | 10 分钟内 ≥20% 且 ≥10 次 | 附 provider/model/feature | 15 分钟聚合 |
| 全站日预算 | P1 | 达到 50%/80%/100% `AI_DAILY_BUDGET_GLOBAL_USD` | 50/80 提醒；100 停止/告警 | 每档一次/天 |
| 用户预算/余额异常 | P1/P2 | 余额为负、单日扣费异常、未知价调用 | P1 负余额；P2 日报 | 1 小时 |
| 备份缺失/失败 | P1 | >26 小时无新备份、大小为 0、`restore_drill` 失败 | 附路径/日志 | 6 小时 |
| 磁盘水位 | P1/P0 | >85% P1；>95% P0 | 附 `df -h` | 6 小时 |
| 证书到期 | P1 | <14 天或续期失败 | 附域名/到期日 | 1 天 |
| 邀请码爆破 | P1 | 失败 >20/小时/IP 或 >100/天 | 附 IP 哈希/次数 | 1 小时 |
| 管理员操作 | P2 | 调余额、封禁、维护模式；删除执行按 §4.3.5 走 P1 | 审计通知 | 不 dedup（逐条） |
| 成本对账差异 | P1 | 月度差异 >5% 或未定价调用 >0 | 附对比表 | 每天 |

> 阈值是建议值；M5 根据真实流量调整，避免告警疲劳。

### 9.5 去重、静默、分级

- **fingerprint**：`env + event + scope`（如 `prod:healthz:db`）；同一 fingerprint 在 `ALERT_DEDUP_SECONDS` 内只发一次；恢复时发一条“已恢复”。
- **分级**：P0 立即 @负责人；P1 聚合（15 分钟窗口）后发；P2 每日摘要。不要所有事件 @all。
- **静默**：维护模式/已知发布窗口内，P1/P2 静默；P0 仍发。静默必须有结束时间，不能永久。
- **抑制**：同一根因（如 DB 挂了导致 healthz + 5xx + 登录失败）合并为一条主告警，附关联事件，避免刷屏。
- **恢复通知**：P0/P1 恢复时发一条；避免“告警后不知道是否恢复”。

### 9.6 无外网/飞书不可用降级

- 发送失败：写 `data/alerts/failed.jsonl`（脱敏，不含 webhook/secret）；记日志；下一次巡检重试；不阻塞业务。
- 无外网：同上；`/healthz` 可增加只读 `alerts.last_success_at`（不暴露密钥）；管理员可在服务器看 `failed.jsonl`。
- 飞书限流/5xx：指数退避（最多 3 次）；仍失败则落盘；不要因为告警失败让应用 500。
- 服务器时间必须 NTP 同步；签名依赖时间戳；时间漂移会导致飞书拒绝。
- 监控本身要有“心跳”：每日发一条“巡检正常”摘要（P2），否则“没消息”无法区分“正常”与“告警器挂了”。

### 9.7 测试与验收

- `ALERT_DRY_RUN=1` 本地跑，检查消息格式/去重/脱敏。
- 真实发一条测试消息到群；确认收到、@人正确。
- 模拟 `/healthz` 503、备份缺失、磁盘阈值、LLM 失败（mock/测试环境），确认级别/去重/恢复。
- 故意让 webhook 错误/断网，确认业务不受影响、`failed.jsonl` 有记录。
- 检查 `grep -R "FEISHU_WEBHOOK"` 仓库无真实值；日志无 webhook/secret。
- 验收人：用户本人；证据：截图/日志/告警记录。

### 9.8 风险

- webhook 泄露 = 任何人可发消息/钓鱼；轮换、最小权限、群设置。
- 告警疲劳：阈值太敏感；先观察一周再收紧。
- 飞书不可用/限流；不要当唯一监控。
- 单人运营：P0 夜间可能无人响应；至少保证消息可达 + 次日处理；不建议承诺 24/7。
