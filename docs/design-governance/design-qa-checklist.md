# 设计 QA 清单（按功能模块）

> 版本：v0.1（2026-11-19）｜责任人：A5（质量门禁与 QA）｜审批：lead
> **状态：阶段 0 框架，未最终化。** 本清单只搭模块与占位检查项，**不是**已验收的测试用例；每个模块的检查项都要等 **A1 审计报告 + 阶段 1/2 规范（A2 令牌 / A3 交互导航）** 出来后，在阶段 3 逐条替换/补全并挂上审计问题号。
> 与 [`design-gate.md`](./design-gate.md) 的分工：门禁是**每个 UI PR 的 7 项最小集**；本清单是**发布前/阶段回归的模块全量集**，两者不互相替代。

---

## 0. 怎么用

### 0.1 两种用法

1. **PR 级（快速）**：只跑 `design-gate.md` 的 G1–G7 + 5 分钟走查，不跑本清单。
2. **阶段/发布级（全量）**：上线前或阶段门禁时，按「本次改动触及的模块 + 横切项」跑一遍；全绿才发布，P0 即停。

### 0.2 走查环境矩阵

| 维度 | 取值 | 何时必测 |
|---|---|---|
| 宽度 | 375 / 768 / 1024 / 1440 | 375 + 1440 每次；改导航壳加 768 / 1024 |
| 语言 | zh-CN / vi-VN | 改文案、布局、日期/数字格式时 |
| 身份 | 游客 / 登录用户 / 管理员 | 涉及门禁、账户、管理台时 |
| 数据状态 | 空 / 加载 / 错误 / 离线 | 涉及列表或异步请求时 |
| 输入方式 | 键盘 / 触屏 / `prefers-reduced-motion` | 涉及交互或动效时 |

### 0.3 结论怎么记

- 每项只有 **☐ 是 / ☐ 否**；不适用写 `N/A` **并给一句理由**（没有理由的 N/A 视为未通过）。
- 「否」→ 记 `编号 + 一句现象 + 等级 + 负责人`，贴到 PR 或发布清单；不要只写「有问题」。
- 证据：截图（文件名带宽度与语言，如 `reader-375-vi.png`）、命令输出、或 `data-testid` 片段。仓库已有 800+ 处 `data-testid`，优先复用它定位。
- **没跑过的项不许勾「是」**；不确定就留空并在清单末尾记「未覆盖」。

### 0.4 阶段 3 的补全规则（硬约束）

1. 每条检查项必须能对应至少 1 个 A1 审计问题号；无对应关系的 → 删除，或显式标「新增预防项」并给理由。
2. 反向：A1 的每个 P0/P1 问题至少要落到 1 条检查项（否则该问题必然复发）。
3. 检查项必须写「怎么判定」，不能只写「保持一致」「体验良好」这类不可验证的话。
4. 等级在阶段 3 用 A1 的分级对齐；本版等级只是占位。

### 0.5 范围边界

- 本清单覆盖 **Web 端**（含响应式到 375px）。`mobile/` Expo 原生 app 本轮不在治理范围（章程 §1），恢复跟进时另起模块。
- 课程（第 6 模块）功能已存在，但按章程 §1 **推迟到上线后**，本轮不作为发布阻塞；清单保留，恢复投入时启用。
- 后端行为正确性不在本清单内（由 specs 与后端测试负责）；这里只看用户可见结果。
